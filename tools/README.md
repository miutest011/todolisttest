# 测试工具

待办清单项目的自动化测试。没有任何依赖，不用装 npm、不用命令行，浏览器打开就能跑。

## 怎么用

**每次改完功能，打开 `tools/test.html` 看一眼。**

> ⚠️ **本地起服务器一定要用 `python3 tools/dev-server.py`**，别用 `python3 -m http.server`。
> 自带的那个不发缓存头，浏览器会自作主张缓存文件，导致你改完代码刷新看到的还是旧版本。
> 这个坑连续踩过四次才找到根源，为此做了三层防护：dev-server 明确禁止缓存、
> 测试页动态加载脚本时自动带时间戳、`sw.js` 里本地 localhost 一律网络优先。

两种打开方式都可以：

- 直接双击 `tools/test.html`（少数要读项目文件的检查会显示"跳过"）
- 或者启动本地服务器后访问 `http://localhost:4173/tools/test.html`（推荐，所有检查都会跑）

页面顶部会显示汇总：

- **全部通过：215 条（已连跑两遍）** → 绿色，说明原有功能都没被改坏
- **N 条失败** → 红色，下面会列出是哪几条测试挂了、以及"期望值 / 实际值"分别是什么
- **N 条结果不稳定** → 黄色警告条，说明测试之间有状态泄漏（见下）
- **N 条没有断言** → 黄色警告条，说明有测试什么都没验证（见下）
- **跳过 N 条** → 灰色，当前环境跑不了的检查（比如双击打开时读不了文件），换成本地服务器打开就会跑

改了代码之后点"重新运行"按钮就能再跑一遍，不用刷新页面。

### 运行器自带的三个机制

**① 每次都连跑两遍，比对结果**

如果某条测试改了全局状态却没还原，第一遍常常看不出来，要等下一遍才露馅——
这种"结果取决于执行顺序"的问题最难查。所以运行器每次都跑两遍，
两遍结果不一致就直接报出来，并列出是哪些测试受了影响。

跑两遍的代价是不到 1 秒，换来这类问题永远自动现形，很划算。

**② 统计每条测试做了几次断言**

一次断言都没做的测试会被标黄。这种"假测试"看着有、实际什么都没验证，
比没写测试更危险——它会让你误以为有保障。

**③ 跳过**

有些检查只能在特定环境下跑——比如要读项目里的文件，双击打开测试页时浏览器不让读。
这时在测试里调用 `skip('原因')`，这条会显示成灰色的"跳过"：既不算失败，
也不会被当成没有断言的假测试，汇总栏会写"跳过 N 条"，免得你以为它也验证过了。

**别用 `skip` 绕开真正的失败**——它只该用在"这个环境下根本没法检查"的情况。

## 文件说明

| 文件 | 作用 |
|---|---|
| `test.html` | 测试页面，打开它就会自动跑所有测试并显示结果 |
| `test-runner.js` | 极简测试框架：`test()` 登记测试、`assert()` / `assertEqual()` 做断言、`skip()` 跳过、`createMemoryStorage()` 提供假存储、连跑两遍比对结果 |
| `tests.js` | 待办清单相关的测试，以及 `setup()`、`click()` 这些公共工具 |
| `tests-logs.js` | 打卡功能的测试（用到 `tests.js` 里的工具，所以排在它后面加载） |
| `dev-server.py` | 本地开发服务器（不缓存任何文件） |
| `make-icons.py` | 生成 PWA 应用图标 |

被测试的代码是上一层目录的 `../app.js` 和 `../logs.js`。

**新加测试文件时，记得加进 `test.html` 里的 `SCRIPTS` 列表**，否则里面的测试根本不会跑——而且不会有任何报错。

## 测试内容

目前 215 条，分这几类：

**数据操作**：添加任务（空内容不添加、自动去空格）、勾选完成、重命名、移动到别的清单、删除。

**清单管理**：新建（重名/空名不创建）、重命名、上移下移排序（头尾不越界）、删除。

**清单改名的连带同步**：改名后，里面任务的归属和折叠状态记录都要跟着改——不同步的话任务会从界面上"消失"。

**删除清单的确认**：空清单不弹确认；有任务时弹确认且提示里带数量；用户点"取消"什么都不删；点"确定"才连任务一起删。

**存储与老数据兼容**：存了再读回来内容一致；老数据缺 `category` 字段时自动归到第一个清单；任务的清单不在列表里时自动补上，避免任务看不见。

**界面渲染**：任务按清单正确分组、折叠后不显示任务且箭头变 `▸`、已完成任务带删除线样式、标题上的数字只数未完成的。

**界面交互**（踩过的坑都留了测试，防止改代码时再掉进去）：

- 点勾选框只切换完成状态，**不会跳到详情页**（靠 `stopPropagation` 拦住）
- 点任务任意位置（含文字）都进详情页，点返回回列表
- 详情页里点标题改名，回车保存 / Esc 取消
- 连续添加任务时输入框保持打开，空着回车才结束
- 三点菜单：点开、点别处关掉、菜单开着时点任务只关菜单不进详情页
- "移动到"只列出别的清单，第一个清单没有"上移"、最后一个没有"下移"

**开始时间与截止时间**：创建任务时自动记录开始时间；开始时间只在详情页显示、列表页不显示；老任务缺时间字段时显示"未记录"而不是报错；点时钟图标展开编辑区；保存后写入数据并显示；没选日期不保存；清除时连提醒设置一起清掉；改了截止时间后"已提醒"标记会重置。

**到点提醒**：还没到时间不弹；到点弹一次且内容里带任务名；同一条不重复提醒；"提前 1 天"等时间点算得准（正好到点的弹、差一分钟的不弹）；选了"不提醒"、已完成、没设截止时间的都不弹；通知被浏览器拦下时不标记为已提醒（以后授权了还能收到）；只有选了提醒才申请通知权限；没授权时详情页给出提示。

**备注与附件**：备注初始为空、失去焦点时自动保存；附件添加后文件内容进仓库、信息记在任务上；一次能加多个；删附件时记录和文件一起清掉；**删任务、删清单时附件文件也一起清掉**（否则会留下永远占空间的垃圾文件）；存不下时给出提示且不会留下打不开的空附件。

**置顶**：切换状态并保存；置顶的排到清单最前、其余保持原顺序；只在自己所在的清单内生效、不会串到别的清单；点置顶按钮不会误跳进详情页。

**已完成 / 已放弃分组**：做完的从主列表移进"已完成"折叠分组；分组默认收起、点击可展开收起；一条都没有时不显示分组；主列表里置顶的在最上；标记完成时自动取消置顶；已完成的不显示置顶按钮；取消完成后回到主列表、分组空了就消失；拖拽落点和页面看到的顺序一致（列表渲染和拖拽算位置共用同一个排序函数，避免两边规则跑偏）。

**放弃**：菜单里能放弃，任务进入"已放弃"分组；**放弃不是删除，记录和备注都完整留着**（这正是它和删除的区别）；勾选框显示成灰色的叉而不是勾；能"重新拾起"回到未完成，点勾选框也能恢复；已放弃的菜单里没有"标记为完成"；放弃时取消置顶、标题数字不再算它；已放弃的不会再提醒；已完成和已放弃是两个独立分组、各自展开互不影响；详情页会显示状态。

**三状态迁移**：老数据的 `done: true/false` 自动变成 `status: 'done'/'active'`，并把老字段清掉——两个地方都记状态早晚会对不上。

**页面顶部的悬浮按钮（可复用组件）**：待办详情页和打卡详情页用的是同一个 `createPageHeader`——左边圆形返回键（里面是画出来的 SVG 箭头，不是文字符号）、右边圆形 ⋯ 菜单。两个页面各有一条测试盯着：顶部那一行在不在、两个按钮是不是圆形款、**菜单是不是真从卡片里挪走了**（卡片里不该还留一个）。以后别的页面用这个组件，照着这两条写就行。

**详情页操作**：⋯ 菜单在右上角，里面能改名、移动、标记完成、删除；置顶按钮留在卡片里；点标题直接改名；删除后回到列表页。

**拖拽排序**：同清单内前移后移；跨清单拖到指定位置；拖进空清单；位置越界时放到最后；拖动不会弄丢任务的其它字段；清单按新顺序重排；**顺序对不上时拒绝写入**（少了、多了、出现不存在的清单都拒绝，避免把数据弄丢）。界面部分：整行任意位置都能拖；拖动时会浮起一份跟手的副本、松手后收掉；手机上按住不动才开始拖（直接滑动是滚页面）；只点一下没拖动时什么都不做；拖完之后紧跟的那次点击不会误进详情页、不会误折叠清单；按在勾选框上不会启动拖动。

**点击行为**（专门防误触，都是手机上实测暴露的问题）：点任务的任何位置（含文字）都是进详情页、不会变成改名；点清单标题任何位置（含名字）都是折叠；改名统一走详情页标题或 ⋯ 菜单，两条路都有测试守着。

**底部标签栏**：默认停在"清单"页；点"今天"能切过去、再点能切回来、高亮状态跟着变；详情页上不显示标签栏（它是盖在上面的一层）；**每次启动都回到"清单"页**（这条是补状态泄漏时加的，见下）。

**"今天"页**：显示今天到期的任务；过期的单独一组排在前面；汇总所有清单并标出任务属于哪个清单；已完成和已放弃的不出现；明天到期的不算今天；空状态会提示"给任务设置截止时间后会出现在这里"而不是干巴巴一句没有任务；点任务能进详情页；在这一页勾选完成后任务立刻消失；**这一页的任务不能拖拽**（混着不同清单，没有"顺序"可言）。

**打卡：数据**：新增项目带 id 和空记录；空名和重名不能新增；记一次追加一条当前时间；改名只改名字，id 和记录不变（用 id 认人，改名不用到处同步）；删除有记录的项目要确认，取消不删、确认后连记录一起删；没记录的直接删；**按本地日期统计每天几次，凌晨 0:30 和晚上 23:30 都算在同一天**（偷懒取 ISO 字符串前 10 位会算错——测试机在 UTC-7，这个 bug 是真会发生的）；"上次打卡"说成人话（还没打过 / 今天 / 昨天 / N 天前，看的是最近一次）；月历周一开头、1 号对得上星期几；闰年二月 29 天；翻月份能跨年；删某一条记录只删那一条。

**打卡：列表页**：底部有"打卡"标签；没项目时有空状态；大数字是累计总次数（跨月的也算）；点"+ 新增打卡"输入回车就创建；**点数字只 +1，不进详情页**；点卡片其它地方进详情页，不会顺手记一次；打卡后出现撤销提示，**撤销只撤刚才那一次**（之前的记录要留着）；提示过一会儿自己消失，而且消失不等于撤销；重开应用时提示不残留。

**打卡：详情页**：顶部是那套通用的悬浮圆按钮（返回 + ⋯ 菜单）；下面横排三个小方块（总次数 / 本月 / 上次打卡），"上次打卡"显示的是"今天 / 昨天 / N 天前"这种短说法而不是完整时间；**打过卡的日子用手写风格的圈圈出来，一天打几次都只有一个圈**（次数看下面的记录列表）；今天用灰底圆标出，刚进详情页默认选中今天；点别的日期，下面就换成那天的记录，同时只能选中一天；选中没打过卡的日子会给一句"这天还没有打卡"；翻到别的月份默认选中那个月 1 号；详情页点数字也能记一次，三个小方块、月历圈和记录列表都立刻跟着更新；删某一条记录要先确认；⋯ 菜单改名；⋯ 菜单删除后回到打卡列表；不显示标签栏、返回回到打卡页；重开应用时详情页状态（在看哪个项目、翻到哪个月、选中哪一天）全部清掉。

**打卡：补录**：只有**已经过去、又没打过卡**的日子才出现"+ 补录一次"——今天不显示（直接点大数字更快），还没到的日子也不显示，那天已经有记录时同样不显示；点开是个填时间的小编辑区，默认 12:00；确定后补上一条，那天立刻被圈出来、总次数加一、记录列表里出现，补录入口消失；点取消、或时间空着都不会加记录；**填的是本地时间**（凌晨 00:30 和深夜 23:30 都必须落在当天，见下面那条经验）；补上的记录和平常打的完全一样，能照常删掉；重开应用时补录状态会清掉。

**打卡：标签与归档**：新增标签带 id 并保存，空名、重名、以及叫"所有""已归档"的都不行（会和顶部固定项分不清）；标签改名只改名字，项目靠 id 照样还在这个标签下；删除有项目在用的标签要确认、取消不删，**确认后项目和记录都在，只是身上少了这个标签**；没人用的直接删；新增项目时不存在的和重复的标签 id 会被去掉；一个项目可以有多个标签，点一下加、再点去掉；**归档会清掉所有标签，取消归档后标签不会自己回来，归档的项目加不了标签**；老数据没有标签字段时补默认值，指向已删标签的 id 会被清掉；筛选规则："所有"不含已归档、某个标签只列带它的、"已归档"只列归档的。

界面部分：顶部顺序是 所有 / 自己的标签 / 已归档 / + 新增，默认选中"所有"；点标签只看这一类、高亮跟着走；**"已归档"下面没有新增入口**（新建的不是归档状态，建完就会从这一页消失）；三种"空"各有各的提示；"+ 新增"回车创建、Esc 不建，光标自动放进输入框。新增打卡时：**点标签不会把已经打的名字清掉**（点标签会让页面重画）；"创建"和"取消"按钮都能用；停在某个标签下时默认带上它，建完还在；把默认的标签取消掉的话，建完切回"所有"，免得以为没建成；在编辑区里新建标签会自动选上，**光标进的是标签输入框而不是上面的名字输入框**。详情页：点标签加上 / 去掉；详情页里新建的标签直接加到这个项目上；⋯ 菜单归档后标签清空、给出说明、菜单变成"取消归档"、列表里去了"已归档"；取消归档后又能选标签。标签管理：**手机上长按出现改名 / 删除，抬手时浏览器补发的那次点击不会把它关掉**；按住时手指滑动（在横着滑标签行）不算长按；电脑上右键也行，"所有""已归档"不能管理；改名；删掉正在看的标签会回到"所有"。重开应用时选中的标签、输入、管理条、新增编辑区全都清掉；**冷启动时项目身上的标签能读回来**（必须先读标签再读项目，见下面"侥幸通过"的第二个例子）。

**工程检查**：`index.html` 加载的每个本地脚本都必须出现在 `sw.js` 的缓存列表里——漏了的话装成 App 离线打开会缺文件，而功能测试对这类问题完全是盲的。这条要读项目文件，双击打开测试页时会显示"跳过"。

**性能**：一个项目 3650 条打卡记录（每 4 小时一次、大约 600 天），切到打卡页再进详情页要在 300ms 内。打卡每点一次就多一条记录，是这个项目里数据增长最快的部分。

**自检**（验证测试工具本身可靠，7 条）：

- 值不相等时 `assertEqual` 确实会报错、条件为假时 `assert` 确实会报错——如果断言函数写坏了，所有测试都会假装通过，那这套工具就没意义了
- **`assertEqual` 拒绝比较两个页面元素**，并提示改用 `assert(a === b)`；和 `null` 比较不受影响（见下面"两个元素永远相等"）
- **异步测试失败时不会被悄悄吞掉**——运行器如果漏掉一个 `await`，`async` 测试里的失败就会被吃掉、全部假装全绿
- `skip()` 发出的是"跳过"信号，运行器能把它和真正的失败区分开
- 每条测试的数据互相独立，不会串
- **跑测试不会碰到你浏览器里真实的待办数据和附件**（测试用的是内存里的假存储和假附件仓库）

## 怎么加新测试

照抄现有写法，三步：准备环境 → 操作 → 检查结果。

```js
test('这个功能应该怎样', () => {
  setup({ categories: ['工作'] });      // 准备一份干净的假数据

  addTodo('工作', '写周报');            // 执行操作

  assertEqual(todos.length, 1, '应该有一条任务');   // 检查结果
});
```

`setup()` 可以传入初始数据：`{ categories: [...], todos: [...], collapsed: [...], logItems: [...], logTags: [...] }`，不传就是默认状态。它会自动把应用挂到一个临时元素上、跑完自动清理，并且把这些东西都换成假的或恢复成默认值：

| 真实环境 | 测试里换成 | 好处 |
|---|---|---|
| `localStorage` | 内存里的假存储 | 不会碰你真实的待办数据 |
| `confirm()` | 直接返回 true（可改） | 不会真的弹窗卡住测试 |
| 当前时间 | 固定在 `FIXED_NOW` | 时间相关的判断才有确定答案 |
| 系统通知 | 记录到 `notifications` 数组 | 不会真的往屏幕上弹通知 |
| `IndexedDB` 附件仓库 | 内存里的假仓库 `blobs` | 不会往你硬盘上写文件，还能直接查文件存没存进去 |
| 长按判定时间 | 0 | 不用每条测试真等半秒 |
| 撤销提示显示时长 | 每条测试恢复成 4 秒 | 有测试会把它改短，不还原就会泄漏到后面的测试里 |

**附件相关的测试要写成 `async`**，因为存取文件是异步的。运行器两种写法都支持：

```js
test('附件：添加后文件真的存进去了', async () => {
  const { blobs } = setup({ categories: ['工作'] });
  addTodo('工作', '写周报');

  await addAttachments(0, [fakeFile('图.png', 'image/png')]);

  assertEqual(blobs.files.size, 1, '文件内容应该存进仓库');
});
```

需要模拟用户点击时用 `click(元素)`，模拟按键用 `press(元素, 'Enter')`。

测时间相关的功能时，用 `isoAfter(分钟数)` 构造"相对现在多久之后"的时间，再调 `checkReminders()` 检查该不该提醒——不用真的等，也不用碰定时器：

```js
test('提醒：到点了会弹通知', () => {
  const { notifications } = setup({
    categories: ['工作'],
    todos: [{ text: '交报告', status: 'active', category: '工作',
              createdAt: FIXED_NOW, dueAt: isoAfter(60), remindBefore: 60, reminded: false }]
  });

  checkReminders();     // 离截止 60 分钟，设的提前 60 分钟 → 该响了

  assertEqual(notifications.length, 1, '应该弹出一条通知');
});
```

**测"按日期统计"这类功能时，用本地时间造数据**（`tests-logs.js` 里的 `localIso(年, 月, 日, 时, 分)`），
而且**必须凌晨和深夜各来一次**。只挑一个时间点是不够的，理由见下面"测试可能只是侥幸通过"。

**做可复用组件时，测"它长什么样"而不只是"它在不在"**。顶部那两个悬浮圆按钮就是例子：
只断言 `.menu-btn` 存在的话，"忘了套圆形样式"这种问题一点都抓不到；
把 `.round-btn`、`svg`、"卡片里不该还留一个菜单"都断言上，组件的约定才算真的守住了。

**比较任务对象时，别直接拿整个对象去比**，用 `pick(todos[0], ['text', 'status'])` 只挑关心的字段。否则以后每加一个新字段（比如后来加的时间字段），这种断言都会误报一次失败——这个坑已经踩过了。

**注意一个坑**：每次点击都会让页面整个重画，之前拿到的元素引用就作废了。所以每一步操作之后要重新从 `root` 上查一遍，不能把元素存起来跨点击使用：

```js
const { root } = setup(...);
click(root.querySelector('.todo-text'));
const input = root.querySelector('.edit-input');   // ← 点击之后重新查，不能用点击前存的引用
```

**建议：修 bug 的时候一定顺手补一条测试**，这样同一个 bug 不会回来第二次。

以后新增测试后，可以用同样的办法抽查一下：把对应功能故意改坏，确认测试真的会变红，再改回来。

**注意变异本身也可能是无效的**：有一次我把"置顶排序"改成先全局排序再按清单过滤，测试全绿——查下来是这个改法根本没造成可观察的差异（过滤之后每个清单内部顺序还是对的），不是测试有漏洞。换成"干脆不排序"之后立刻就被抓到了。所以测试没变红时，先确认你的破坏是真的破坏。

**但有时候真的是测试写错了**。做"今天"页时，我写了一条"这一页不能拖拽"的测试，看起来很合理：

```js
drag(items[0], ...);                                    // 拖一下
assertEqual(document.querySelector('.drag-ghost'), null);   // 检查没有浮起副本
```

变异测试发现它抓不到任何问题——因为 `drag()` 里已经包含了"松手"，而副本在松手时本来就会被移除。**这条断言永远成立，等于没写。** 正确的写法是在拖动**进行中**检查（发完 `pointermove` 就断言，先别 `pointerup`）。

这类"假测试"是最危险的：它让你以为有保障，实际什么都没测。**只有变异测试能发现它们。**

### 测试可能只是"侥幸通过"

比"假测试"更隐蔽的一种：断言写对了，但选的数据恰好碰不到 bug。

做补录时我写了一条测时区的测试，补录时间填 23:30，断言这条记录要落在选中那天。
然后故意把代码改成"把用户填的时间当成 UTC"——**这条测试居然是绿的**。

原因：本机在 UTC-7，`23:30Z` 换算回本地是当天 16:30，日期没变，所以看不出来。
换成 UTC+8 的机器，同样的 bug 立刻就会让这条测试变红。
也就是说，**这条测试能不能发现问题，取决于跑它的机器在哪个时区**——这比没有测试更糟，
因为它给了你一种虚假的安全感。

改法是凌晨和深夜各补一次，断言两次都落在同一天：

```js
backfillLog('log-喝水', '2026-09-06', '00:30');
backfillLog('log-喝水', '2026-09-06', '23:30');
assertEqual(countLogsByDay(logItems[0])['2026-09-06'], 2, '两次都该算在 9 月 6 日');
```

不管在哪个时区，这两个时间点里总有一个会跨过午夜。加强之后重跑那个变异，
报错变成了 `{"2026-09-05":1, "2026-09-06":1}`——一眼就能看出问题在哪。

**经验**：测和"边界"有关的功能（时区、月初月末、跨年、正好到点），
一个样例往往不够，要挑**边界两侧**的样例。

**第二个例子：内存里的"剩饭"帮 bug 打了掩护。**
读项目时要对照标签列表清理无效的标签 id，所以启动时必须先读标签、再读项目。
我专门写了一条"重开应用后项目身上的标签还在"的测试，然后故意把读取顺序对调——**它是绿的**。

原因：`logTags` 是全局变量，这条测试自己前面几步（甚至上一条测试）已经把同样 id 的标签留在了内存里。
读项目时对照的是这份"剩饭"，所以顺序错了也照样对得上。
可手机上真正冷启动时内存是空的，**用户所有项目的标签会在打开 App 的一瞬间全部消失**。

改法是在测试里先把内存清空（`logTags = []; logItems = [];`）再 `initApp()`，模拟真正的冷启动。

**经验**：测"启动 / 读数据"相关的逻辑时，先把内存里的数据变量清空，
否则你测到的可能是上一步留下的东西，而不是从存储里读出来的。

### 两个元素永远"相等"

做新增标签时，我写了 `assertEqual(document.activeElement, input, '光标要自动放进去')`。
变异测试把"光标放进这个输入框"的代码删掉——**测试是绿的**。

原因在测试工具本身：`assertEqual` 是把两边转成 JSON 再比，而**所有页面元素转成 JSON 都是 `{}`**。
所以拿任意两个元素去比，永远相等。光标在不在输入框里，这条断言根本看不出来。

这比某一条测试写错更严重，因为谁都可能再写出同样的代码。所以改的是工具：
**`assertEqual` 现在碰到两边都是元素时直接报错**，并提示改用 `assert(a === b, ...)`。
和 `null` 比较（"这个元素应该已经不在了"）是正常用法，不受影响。有一条自检盯着这个行为。

## 测试之间不能互相影响

跑两遍测试，两遍结果必须一样。如果第二遍开始出现莫名其妙的失败，通常是某条测试改了全局状态却没还原。

已经踩过的两个：

- `currentTab`（当前在哪个标签页）没被 `resetViewState()` 重置，导致"今天"页的测试跑完后，后面所有测试都在错误的页面上运行
- `suppressNextClick`（拖动后忽略一次点击的标记）在拖拽中途失败时被留成 `true`，把下一条测试的第一次点击吞掉了

两个都是在 `app.js` 的 `resetViewState()` 里补上重置解决的。打卡模块的界面状态放在 `logs.js` 的 `resetLogViewState()` 里，由 `resetViewState()` 统一调用。

**现在这件事已经自动化了**：运行器每次都连跑两遍并比对结果，不一致就报警。
所以这类问题以后会自己冒出来，不用再靠碰巧发现。

**但有一种情况不会出现"不稳定"警告**：如果上一轮已经把状态弄脏了，两遍会一模一样地失败。
打卡模块做变异测试时就碰到了——漏了重置详情页状态，结果是 93 条测试一起挂，而不是黄色警告。
所以**看到几十条毫不相干的测试同时失败，第一反应也应该是状态泄漏**，而不是去一条条查。

新增全局状态变量时，记得问一句：**它需要在 `resetViewState()`（或 `resetLogViewState()`）里重置吗？**
凡是"界面当前处于什么状态"的变量，答案基本都是要。
