# 测试工具

待办清单项目的自动化测试。没有任何依赖，不用装 npm、不用命令行，浏览器打开就能跑。

## 怎么用

**每次改完功能，打开 `tools/test.html` 看一眼。**

> ⚠️ **本地起服务器一定要用 `python3 tools/dev-server.py`**，别用 `python3 -m http.server`。
> 自带的那个不发缓存头，浏览器会自作主张缓存文件，导致你改完代码刷新看到的还是旧版本。
> 这个坑连续踩过四次才找到根源，为此做了三层防护：dev-server 明确禁止缓存、
> 测试页动态加载脚本时自动带时间戳、`sw.js` 里本地 localhost 一律网络优先。

两种打开方式都可以：

- 直接双击 `tools/test.html`（少数要读项目文件的检查会显示"跳过"）
- 或者启动本地服务器后访问 `http://localhost:4173/tools/test.html`（推荐，所有检查都会跑）

页面顶部会显示汇总：

- **全部通过：401 条（已连跑两遍）** → 绿色，说明原有功能都没被改坏
- **N 条失败** → 红色，下面会列出是哪几条测试挂了、以及"期望值 / 实际值"分别是什么
- **N 条结果不稳定** → 黄色警告条，说明测试之间有状态泄漏（见下）
- **N 条没有断言** → 黄色警告条，说明有测试什么都没验证（见下）
- **跳过 N 条** → 灰色，当前环境跑不了的检查（比如双击打开时读不了文件），换成本地服务器打开就会跑

改了代码之后点"重新运行"按钮就能再跑一遍，不用刷新页面。

### 运行器自带的三个机制

**① 每次都连跑两遍，比对结果**

如果某条测试改了全局状态却没还原，第一遍常常看不出来，要等下一遍才露馅——
这种"结果取决于执行顺序"的问题最难查。所以运行器每次都跑两遍，
两遍结果不一致就直接报出来，并列出是哪些测试受了影响。

跑两遍的代价是不到 1 秒，换来这类问题永远自动现形，很划算。

**② 统计每条测试做了几次断言**

一次断言都没做的测试会被标黄。这种"假测试"看着有、实际什么都没验证，
比没写测试更危险——它会让你误以为有保障。

**③ 跳过**

有些检查只能在特定环境下跑——比如要读项目里的文件，双击打开测试页时浏览器不让读。
这时在测试里调用 `skip('原因')`，这条会显示成灰色的"跳过"：既不算失败，
也不会被当成没有断言的假测试，汇总栏会写"跳过 N 条"，免得你以为它也验证过了。

**别用 `skip` 绕开真正的失败**——它只该用在"这个环境下根本没法检查"的情况。

## 文件说明

| 文件 | 作用 |
|---|---|
| `test.html` | 测试页面，打开它就会自动跑所有测试并显示结果 |
| `test-runner.js` | 极简测试框架：`test()` 登记测试、`assert()` / `assertEqual()` 做断言、`skip()` 跳过、`createMemoryStorage()` 提供假存储、连跑两遍比对结果 |
| `tests.js` | 待办清单相关的测试，以及 `setup()`、`click()` 这些公共工具 |
| `tests-logs.js` | 打卡功能的测试，包括共用标签界面的细节（用到 `tests.js` 里的工具，所以排在它后面加载） |
| `tests-list-tags.js` | 清单页的标签和归档（用到前两个文件里的工具） |
| `tests-mobile.js` | 手机体验：右下角新建按钮、新建面板、防止页面被放大 |
| `tests-gestures.js` | 手指滑动：详情页往右滑返回、列表区左右滑切换标签（用到前面几个文件里的工具） |
| `platform.html` | **平台自检页**：把我们对平台的假设一条条列出来，到真环境里点一遍（见下面「三层防线」） |
| `tests-calendar.js` | 日历页：月 / 周 / 日三种视图、有任务的日子标点、记住选的视图 |
| `tests-native.js` | 为"装成 iOS 应用"做的那些：提醒交给系统、导出 / 导入、和外壳的桥接（`native.js`） |
| `tests-mutate.js` | 变异测试工具自己的测试 |
| `mutate.html` | **变异测试页面**：把代码一处处故意改坏、每次跑全部测试，看测试能不能发现（见下面"怎么确认这套测试是靠谱的"） |
| `mutate-runner.js` | 变异测试的发动机：改代码、在隐藏的测试页里跑、判断结局 |
| `mutations.js` | 变异清单：要故意改坏哪些地方 |
| `dev-server.py` | 本地开发服务器（不缓存任何文件） |
| `make-icons.py` | 生成 PWA 应用图标 |

被测试的代码是上一层目录的 `../app.js`、`../tags.js`、`../calendar.js`、`../logs.js` 和 `../native.js`。
`ios/` 里的 Swift 不在这套测试里 —— 那半只能装到手机上手动确认，清单在 `ios/README.md` 末尾。

**新加测试文件时，记得加进 `test.html` 里的 `SCRIPTS` 列表**，否则里面的测试根本不会跑——而且不会有任何报错。

## 测试内容

目前 401 条，分这几类：

**数据操作**：添加任务（空内容不添加、自动去空格）、勾选完成、重命名、移动到别的清单、删除。

**清单管理**：新建（重名/空名不创建）、重命名、上移下移排序（头尾不越界）、删除。

**清单改名的连带同步**：改名后，里面任务的归属和折叠状态记录都要跟着改——不同步的话任务会从界面上"消失"。

**删除清单的确认**：空清单不弹确认；有任务时弹确认且提示里带数量；用户点"取消"什么都不删；点"确定"才连任务一起删。

**存储与老数据兼容**：存了再读回来内容一致；老数据缺 `category` 字段时自动归到第一个清单；任务的清单不在列表里时自动补上，避免任务看不见。

**界面渲染**：任务按清单正确分组、收起后不显示任务、**清单标题前没有三角**（展开状态用 `aria-expanded` 告诉读屏软件，展开后跟着变）、已完成任务带删除线样式、标题上的数字只数未完成的。

**界面交互**（踩过的坑都留了测试，防止改代码时再掉进去）：

- 点勾选框只切换完成状态，**不会跳到详情页**（靠 `stopPropagation` 拦住）
- 点任务任意位置（含文字）都进详情页，点返回回列表
- 详情页里点标题改名，回车保存 / Esc 取消
- 连续添加任务时输入框保持打开，空着回车才结束
- 三点菜单：点开、点别处关掉、菜单开着时点任务只关菜单不进详情页
- "移动到"只列出别的清单，第一个清单没有"上移"、最后一个没有"下移"

**开始时间与截止时间**：创建任务时自动记录开始时间；**开始时间照样记着，但列表页、详情页都不显示**；老任务缺时间字段时详情页照常打开；**截止时间和提醒合进详情页的闹钟里**：没设时只有灰色闹钟、不写字，点它展开编辑区、再点收起；保存后闹钟变红、写上时间，提醒方式说成人话放进读屏软件能听到的说明里；没设截止时间时闹钟也不提提醒；没选日期不保存；清除时连提醒设置一起清掉；改了截止时间后"已提醒"标记会重置。

**到点提醒**：还没到时间不弹；到点弹一次且内容里带任务名；同一条不重复提醒；"提前 1 天"等时间点算得准（正好到点的弹、差一分钟的不弹）；选了"不提醒"、已完成、没设截止时间的都不弹；通知被浏览器拦下时不标记为已提醒（以后授权了还能收到）；只有选了提醒才申请通知权限；没授权时详情页给出提示。

**备注与附件**：备注初始为空、失去焦点时自动保存；附件添加后文件内容进仓库、信息记在任务上；一次能加多个；删附件时记录和文件一起清掉；**删任务、删清单时附件文件也一起清掉**（否则会留下永远占空间的垃圾文件）；存不下时给出提示且不会留下打不开的空附件。

**置顶**：切换状态并保存；置顶的排到清单最前、其余保持原顺序；只在自己所在的清单内生效、不会串到别的清单；点置顶按钮不会误跳进详情页。

**已完成 / 已放弃分组**：做完的从主列表移进"已完成"折叠分组；分组默认收起、点击可展开收起；一条都没有时不显示分组；主列表里置顶的在最上；标记完成时自动取消置顶；已完成的不显示置顶按钮；取消完成后回到主列表、分组空了就消失；拖拽落点和页面看到的顺序一致（列表渲染和拖拽算位置共用同一个排序函数，避免两边规则跑偏）。

**放弃**：菜单里能放弃，任务进入"已放弃"分组；**放弃不是删除，记录和备注都完整留着**（这正是它和删除的区别）；勾选框显示成灰色的叉而不是勾；能"重新拾起"回到未完成，点勾选框也能恢复；已放弃的菜单里没有"标记为完成"；放弃时取消置顶、标题数字不再算它；已放弃的不会再提醒；已完成和已放弃是两个独立分组、各自展开互不影响；详情页会显示状态。

**三状态迁移**：老数据的 `done: true/false` 自动变成 `status: 'done'/'active'`，并把老字段清掉——两个地方都记状态早晚会对不上。

**页面顶部的悬浮按钮（可复用组件）**：待办详情页和打卡详情页用的是同一个 `createPageHeader`——左边圆形返回键（里面是画出来的 SVG 箭头，不是文字符号）、右边圆形 ⋯ 菜单。两个页面各有一条测试盯着：顶部那一行在不在、两个按钮是不是圆形款、**菜单是不是真从卡片里挪走了**（卡片里不该还留一个）。以后别的页面用这个组件，照着这两条写就行。

**详情页操作**：⋯ 菜单在右上角，里面能改名、移动、标记完成、删除；点标题直接改名；删除后回到列表页。

**空清单提示；三个新建面板都不写小标题**（`tests-mobile.js` 末尾，7 条）：新建任务 / 新建清单 / 新增打卡三个面板从上到下都是"标题、输入框、一排选项、按钮"，**没有小标题**；三个面板里一排选项和输入框之间都留了空；**展开的空清单下面有"该清单内还没有内容，点击添加"**、收起就没有；有任务的清单、只剩已完成任务的清单都不显示（后者下面有"已完成"分组，看得出是展开的）；**点提示弹出新建任务面板，默认放进这个清单**，加完提示消失；菜单开着时点提示只关菜单；**已归档的空清单只说"还没有内容"、点了不弹面板**。

**新建任务面板：闹钟、不写"放进清单"**（`tests-mobile.js`，9 条）：面板里没有"放进清单"几个字，**选中的清单是蓝底**、没选中的不是（量真实样式）；**清单那一排最后是闹钟**，没设时间是灰的、不写字，读屏说明和详情页一样；点闹钟展开设置区、再点收起，保存后闹钟变红写上时间，**打的字和选的清单都不丢**，还没点"添加"不建任务；**加出来的任务带着设好的截止时间和提醒**（准时提醒的 0 也算设了），进详情页闹钟上是同一个时间；没设时间加的任务没有截止时间；**设了提醒会申请通知权限**，没选提醒不打扰；没选日期点保存不保存、设置区留着，设过的可以清除；**回车连续添加时下一条的时间清空、清单保留**；清单那一排和输入框之间留了空。

详情页和新建任务面板用的是**同一个闹钟按钮和同一个设置区**（`createDueButton` / `createDueEditor`），只是选完之后存到不同的地方——一处改了，两处一起变。

**详情页：清单标签 + 闹钟**（`tests.js` 末尾，6 条）：**卡片里没有置顶按钮，也没有"状态""开始时间""截止时间""提醒"这些行**；标题卡片紧下面一行是清单标签和闹钟（先标签后闹钟），标签上写所在的清单；清单标签是虚线框、闹钟没设时间是灰的、设了是红的（量真实样式）；**闹钟旁边的时间说得短**：今天 / 今天凌晨也算今天（按本地日期，不按 UTC）/ 明天 / 昨天 / 几月几日 / 不是今年带年份；在闹钟里设好时间保存后变红、写上"明天 18:30"、编辑区收起。**"今天"页的任务不带置顶按钮**，清单页里照样有，⋯ 菜单还在。放弃的任务在详情页靠勾选框的叉和划掉的标题看出来（原来靠"状态"那一行）。

**拖拽排序**：同清单内前移后移；跨清单拖到指定位置；拖进空清单；位置越界时放到最后；拖动不会弄丢任务的其它字段；清单按新顺序重排；**顺序对不上时拒绝写入**（少了、多了、出现不存在的清单都拒绝，避免把数据弄丢）。界面部分：整行任意位置都能拖；拖动时会浮起一份跟手的副本、松手后收掉；手机上按住不动才开始拖（直接滑动是滚页面）；只点一下没拖动时什么都不做；拖完之后紧跟的那次点击不会误进详情页、不会误折叠清单；按在勾选框上不会启动拖动。

**点击行为**（专门防误触，都是手机上实测暴露的问题）：点任务的任何位置（含文字）都是进详情页、不会变成改名；点清单标题任何位置（含名字）都是折叠；改名统一走详情页标题或 ⋯ 菜单，两条路都有测试守着。

**底部标签栏**：默认停在"清单"页；点"今天"能切过去、再点能切回来、高亮状态跟着变；详情页上不显示标签栏（它是盖在上面的一层）；**每次启动都回到"清单"页**（这条是补状态泄漏时加的，见下）。

**"今天"页**：显示今天到期的任务；过期的单独一组排在前面；汇总所有清单并标出任务属于哪个清单；已完成和已放弃的不出现；明天到期的不算今天；空状态会提示"给任务设置截止时间后会出现在这里"而不是干巴巴一句没有任务；点任务能进详情页；在这一页勾选完成后任务立刻消失；**这一页的任务不能拖拽**（混着不同清单，没有"顺序"可言）。

**打卡：数据**：新增项目带 id 和空记录；空名和重名不能新增；记一次追加一条当前时间；改名只改名字，id 和记录不变（用 id 认人，改名不用到处同步）；删除有记录的项目要确认，取消不删、确认后连记录一起删；没记录的直接删；**按本地日期统计每天几次，凌晨 0:30 和晚上 23:30 都算在同一天**（偷懒取 ISO 字符串前 10 位会算错——测试机在 UTC-7，这个 bug 是真会发生的）；"上次打卡"说成人话（还没打过 / 今天 / 昨天 / N 天前，看的是最近一次）；月历周一开头、1 号对得上星期几；闰年二月 29 天；翻月份能跨年；删某一条记录只删那一条。

**打卡：列表页**：底部有"打卡"标签；没项目时有空状态；大数字是累计总次数（跨月的也算）；点"+ 新增打卡"输入回车就创建；**点数字只 +1，不进详情页**；点卡片其它地方进详情页，不会顺手记一次；打卡后出现撤销提示，**撤销只撤刚才那一次**（之前的记录要留着）；提示过一会儿自己消失，而且消失不等于撤销；重开应用时提示不残留。

**打卡：详情页**：顶部是那套通用的悬浮圆按钮（返回 + ⋯ 菜单）；下面横排三个小方块（总次数 / 本月 / 上次打卡），"上次打卡"显示的是"今天 / 昨天 / N 天前"这种短说法而不是完整时间；**打过卡的日子用手写风格的圈圈出来，一天打几次都只有一个圈**（次数看下面的记录列表）；今天用灰底圆标出，刚进详情页默认选中今天；点别的日期，下面就换成那天的记录，同时只能选中一天；选中没打过卡的日子会给一句"这天还没有打卡"；翻到别的月份默认选中那个月 1 号；详情页点数字也能记一次，三个小方块、月历圈和记录列表都立刻跟着更新；删某一条记录要先确认；⋯ 菜单改名；⋯ 菜单删除后回到打卡列表；不显示标签栏、返回回到打卡页；重开应用时详情页状态（在看哪个项目、翻到哪个月、选中哪一天）全部清掉。

**打卡：补录**：只有**已经过去、又没打过卡**的日子才出现"+ 补录一次"——今天不显示（直接点大数字更快），还没到的日子也不显示，那天已经有记录时同样不显示；点开是个填时间的小编辑区，默认 12:00；确定后补上一条，那天立刻被圈出来、总次数加一、记录列表里出现，补录入口消失；点取消、或时间空着都不会加记录；**填的是本地时间**（凌晨 00:30 和深夜 23:30 都必须落在当天，见下面那条经验）；补上的记录和平常打的完全一样，能照常删掉；重开应用时补录状态会清掉。

**打卡：标签与归档**：新增标签带 id 并保存，空名、重名、以及叫"所有""已归档"的都不行（会和顶部固定项分不清）；标签改名只改名字，项目靠 id 照样还在这个标签下；删除有项目在用的标签要确认、取消不删，**确认后项目和记录都在，只是身上少了这个标签**；没人用的直接删；新增项目时不存在的和重复的标签 id 会被去掉；一个项目可以有多个标签，点一下加、再点去掉；**归档会清掉所有标签，取消归档后标签不会自己回来，归档的项目加不了标签**；老数据没有标签字段时补默认值，指向已删标签的 id 会被清掉；筛选规则："所有"不含已归档、某个标签只列带它的、"已归档"只列归档的。

界面部分：顶部顺序是 所有 / 自己的标签 / 已归档 / + 新增，默认选中"所有"；点标签只看这一类、高亮跟着走；**"已归档"下面没有新增入口**（新建的不是归档状态，建完就会从这一页消失）；三种"空"各有各的提示；"+ 新增"回车创建、Esc 不建，光标自动放进输入框。新增打卡时：**点标签不会把已经打的名字清掉**（点标签会让页面重画）；"创建"和"取消"按钮都能用；停在某个标签下时默认带上它，建完还在；把默认的标签取消掉的话，建完切回"所有"，免得以为没建成；在编辑区里新建标签会自动选上，**光标进的是标签输入框而不是上面的名字输入框**。详情页：点标签加上 / 去掉；详情页里新建的标签直接加到这个项目上；⋯ 菜单归档后标签清空、给出说明、菜单变成"取消归档"、列表里去了"已归档"；取消归档后又能选标签。标签管理：**手机上长按出现改名 / 删除，抬手时浏览器补发的那次点击不会把它关掉**；按住时手指滑动（在横着滑标签行）不算长按；电脑上右键也行，"所有""已归档"不能管理；改名；删掉正在看的标签会回到"所有"。重开应用时选中的标签、输入、管理条、新增编辑区全都清掉；**冷启动时项目身上的标签能读回来**（必须先读标签再读项目，见下面"侥幸通过"的第二个例子）。

**清单：标签与归档**（标签界面和打卡页共用 `tags.js`，界面细节在打卡那边测过，这里测清单自己的规则）：清单标签新增带 id，空名、重名、保留名不行；**和打卡的标签互不相干**，两边能各有一个同名的；标签改名后清单还在标签下；删除有清单在用的标签要确认，确认后清单和任务都在；**像文件夹一样只能放一个**，放进别的标签就从原来那个拿出来，也能"不放进标签"，回到默认值时不留多余记录；归档拿掉标签、取消归档标签不回来、归档的放不进标签；**清单改名时所在标签和归档状态跟着走**（它们按清单名记）；删清单时归属记录一起清掉，再建同名清单不会继承；读数据时理干净（不存在的标签、归档还带标签、不存在的清单）；**冷启动时归属能读回来**；筛选规则；**筛选状态下排序时看不见的清单原地不动**。

界面部分：顶部顺序和默认选中；点标签筛选，"已归档"下没有新建清单的入口；清单页的"+ 新增"和长按改名删除都能用，建的标签不会跑到打卡那边；停在标签下新建清单自动放进去，在"所有"下新建不放；清单 ⋯ 菜单的"放到标签"：当前所在的打勾、点别的就换过去（正在看的标签下它随即消失）、只有在标签下时才有"不放进标签"、一个标签都没有时不显示这组、归档的清单没有这组而是"取消归档"；**筛选状态下拖拽清单能保存**（以前会因为"清单对不上"被拒绝写入）；**筛选状态下上移下移和看得见的邻居换**；**归档清单的任务不出现在"今天"页、到点不提醒且不会被标记成提醒过**，取消归档后恢复；任务的"移动到"不列归档清单；各种空状态；两页的筛选互不影响；换底部页面时收起标签输入框和管理条；重开应用回到"所有"。

**变异测试工具**（12 条）：从 `test.html` 里读出脚本列表，写法变了要明确报"找不到"；路径换算；分得清哪些文件是脚本、哪些要走"拦截 fetch"；原文正好出现一次才改，零次或多次都不改；**替换内容里有 `$` 时原样放进去**（`String.replace` 会把 `$&` 展开）；生成的脚本地址被加上 `?t=` 后代码仍然合法；拼测试页时只换被改的那个脚本、带上 `<base>` 和语法错误记录；对照组一个脚本都不换、也不拦截 fetch；**改 `style.css` 这类文件时，测试 fetch 到的是改过的内容，而且内容里有 `</script>` 也不会把拦截器截断**（真的开一个小 iframe 验证）；结局判断（过期 / 跑不起来 / 加载失败 / 超时 / 抓到 / 没抓到）；**变异清单每条字段齐全、文件确实存在、改动确实有改变、名字不重复**。

**自检**（验证测试工具本身可靠，7 条）：

- 值不相等时 `assertEqual` 确实会报错、条件为假时 `assert` 确实会报错——如果断言函数写坏了，所有测试都会假装通过，那这套工具就没意义了
- **`assertEqual` 拒绝比较两个页面元素**，并提示改用 `assert(a === b)`；和 `null` 比较不受影响（见下面"两个元素永远相等"）
- **异步测试失败时不会被悄悄吞掉**——运行器如果漏掉一个 `await`，`async` 测试里的失败就会被吃掉、全部假装全绿
- `skip()` 发出的是"跳过"信号，运行器能把它和真正的失败区分开
- 每条测试的数据互相独立，不会串
- **跑测试不会碰到你浏览器里真实的待办数据和附件**（测试用的是内存里的假存储和假附件仓库）

| **平台行为假设**（真手指到底发不发某个事件） | `platform.html` 平台自检页（见下） |
| 手感（跟不跟手、流不流畅） | 只能真人在手机上试 |

前两层全自动；第三层一条命令；第四层要动手点几下，但它是唯一能抓住"网页版正常、装进壳里才坏"那类问题的办法。

## 在真 WebKit 里跑一遍

平时开发用的浏览器是 Chromium，手机上是 WebKit，两者有真实差异。同一套测试可以直接搬过去：

```bash
python3 tools/dev-server.py                                        # 先起服务器
xcrun simctl boot "iPhone 15 Pro"; open -a Simulator               # 开模拟器
xcrun simctl openurl booted "http://localhost:4173/tools/test.html"  # 在模拟器的 Safari 里打开
```

失败和跳过的都会列在页面最上面（在手机上滚四百条找红的太痛苦，所以加了这个）。

**第一次这么跑时，四百条里红了 4 条**，全是测试的写法在 iPhone 上不成立，应用本身没问题：

- `blur()` 在**有焦点的窗口**里会真的发 `focusout`（电脑上测试页窗口没焦点，浏览器不发）——两边行为不同，测试里补发的事件就成了第二遍。现在先探测这个环境发不发真事件，发就走真流程。
- iPhone 的 Safari **滚动时不立刻更新 `position: fixed` 元素的坐标**。现在拿一个标准 fixed 元素当尺子，断言"我们的页面和它动得一样多"，哪个引擎都成立。
- Safari 17 **不认 `scrollbar-width`**，而且不认识的声明在解析时就被丢掉，规则对象里也读不到——认的引擎上量计算值，不认的就查样式表原文。
- 探测本身会抢焦点：临时输入框拿到焦点又被删掉，应用于是把 `typing` 摘了。**先探测再设焦点**，顺序反了就是一条飘忽不定的测试（被"连跑两遍"抓到的）。

## platform.html：平台自检页

自动测试测的是**我们的逻辑**，测不了**平台的行为**——因为测试里的事件是它自己造的。
"双击回到今天"就栽在这儿：代码用 `dblclick`，测试自己发 `dblclick`，全绿；可 iPhone 上双击是系统手势，这个事件根本不发。

所以把"我们依赖平台做的事"一条条列出来，到真环境里点一遍：

```bash
# 在应用外壳里打开（confirm、外壳桥接这些只有在壳里才准）
xcrun simctl launch booted com.你的名字.todolist -startPage platform.html

# 或者在手机 / 模拟器的浏览器里打开
xcrun simctl openurl booted "http://localhost:4173/tools/platform.html"
```

里面分两块：**打开就知道的**（数据存不存得住、刷新后还在不在、IndexedDB 能不能开、几个 CSS 属性支持情况、提醒归谁管）和**要动手点的**（连点两下会不会产生两次 click、`dblclick` 发不发、点输入框发不发 focusin、代码能不能设焦点、横滑时能不能拦住滚动、按住不放会不会被系统打断、`confirm()` 会不会弹）。

**什么时候去点**：换了新手机或新系统、改了外壳、加了新的手势或系统交互。
**加了新的平台依赖，就往这一页加一条** —— 这是它的意义所在。

## 怎么加新测试

照抄现有写法，三步：准备环境 → 操作 → 检查结果。

```js
test('这个功能应该怎样', () => {
  setup({ categories: ['工作'] });      // 准备一份干净的假数据

  addTodo('工作', '写周报');            // 执行操作

  assertEqual(todos.length, 1, '应该有一条任务');   // 检查结果
});
```

`setup()` 可以传入初始数据：`{ categories: [...], todos: [...], collapsed: [...], logItems: [...], logTags: [...], listTags: [...], categoryMeta: {...} }`，不传就是默认状态。它会自动把应用挂到一个临时元素上、跑完自动清理，并且把这些东西都换成假的或恢复成默认值：

| 真实环境 | 测试里换成 | 好处 |
|---|---|---|
| `localStorage` | 内存里的假存储 | 不会碰你真实的待办数据 |
| `confirm()` | 直接返回 true（可改） | 不会真的弹窗卡住测试 |
| 当前时间 | 固定在 `FIXED_NOW` | 时间相关的判断才有确定答案 |
| 系统通知 | 记录到 `notifications` 数组 | 不会真的往屏幕上弹通知 |
| `IndexedDB` 附件仓库 | 内存里的假仓库 `blobs` | 不会往你硬盘上写文件，还能直接查文件存没存进去 |
| 长按判定时间 | 0 | 不用每条测试真等半秒 |
| 撤销提示显示时长 | 每条测试恢复成 4 秒 | 有测试会把它改短，不还原就会泄漏到后面的测试里 |

**附件相关的测试要写成 `async`**，因为存取文件是异步的。运行器两种写法都支持：

```js
test('附件：添加后文件真的存进去了', async () => {
  const { blobs } = setup({ categories: ['工作'] });
  addTodo('工作', '写周报');

  await addAttachments(0, [fakeFile('图.png', 'image/png')]);

  assertEqual(blobs.files.size, 1, '文件内容应该存进仓库');
});
```

需要模拟用户点击时用 `click(元素)`，模拟按键用 `press(元素, 'Enter')`。

测时间相关的功能时，用 `isoAfter(分钟数)` 构造"相对现在多久之后"的时间，再调 `checkReminders()` 检查该不该提醒——不用真的等，也不用碰定时器：

```js
test('提醒：到点了会弹通知', () => {
  const { notifications } = setup({
    categories: ['工作'],
    todos: [{ text: '交报告', status: 'active', category: '工作',
              createdAt: FIXED_NOW, dueAt: isoAfter(60), remindBefore: 60, reminded: false }]
  });

  checkReminders();     // 离截止 60 分钟，设的提前 60 分钟 → 该响了

  assertEqual(notifications.length, 1, '应该弹出一条通知');
});
```

**测"按日期统计"这类功能时，用本地时间造数据**（`tests-logs.js` 里的 `localIso(年, 月, 日, 时, 分)`），
而且**必须凌晨和深夜各来一次**。只挑一个时间点是不够的，理由见下面"测试可能只是侥幸通过"。

**做可复用组件时，测"它长什么样"而不只是"它在不在"**。顶部那两个悬浮圆按钮就是例子：
只断言 `.menu-btn` 存在的话，"忘了套圆形样式"这种问题一点都抓不到；
把 `.round-btn`、`svg`、"卡片里不该还留一个菜单"都断言上，组件的约定才算真的守住了。

**比较任务对象时，别直接拿整个对象去比**，用 `pick(todos[0], ['text', 'status'])` 只挑关心的字段。否则以后每加一个新字段（比如后来加的时间字段），这种断言都会误报一次失败——这个坑已经踩过了。

**注意一个坑**：每次点击都会让页面整个重画，之前拿到的元素引用就作废了。所以每一步操作之后要重新从 `root` 上查一遍，不能把元素存起来跨点击使用：

```js
const { root } = setup(...);
click(root.querySelector('.todo-text'));
const input = root.querySelector('.edit-input');   // ← 点击之后重新查，不能用点击前存的引用
```

**建议：修 bug 的时候一定顺手补一条测试**，这样同一个 bug 不会回来第二次。

## 怎么确认这套测试是靠谱的

全绿本身不能说明问题——如果测试根本抓不到 bug，它也会全绿。验证方法是**故意把 `app.js` / `logs.js` 改坏，看测试会不会红**。

### 用 mutate.html 跑

启动 `python3 tools/dev-server.py`，打开 http://localhost:4173/tools/mutate.html ，选一组（或者全部）点"开始"。
它会把 `mutations.js` 里列的地方一处一处改坏，每改一处就把全部测试跑一遍。**只在内存里改，项目文件不会动。**
目前 229 条，全部跑完五分钟左右。

> **跑的时候让浏览器窗口（或预览面板）保持在前台。** 窗口被藏到后台时，浏览器会把页面里的计时器放慢，一条变异从 1 秒拖到十几秒，全部跑完要半个小时。只改了一小块时，可以只选那一组跑。

> **清预览浏览器里的数据之前，先看一眼内容。** 有两次在 localhost 的真实存储里发现多了 `todos`，一开始以为是变异测试把代码改坏时写进去的；后来看了内容才发现是一条随手敲的"q'sqwl"——是用户自己在预览面板里试用时建的。正常跑测试不会写真实存储（有自检盯着，清空后跑完整套也确实是空的）。

**能改的不只是 JS**：测试页加载的脚本直接换成改过的代码；`style.css`、`index.html`、`sw.js` 这些测试用 `fetch` 去读的文件，会在隐藏的测试页里拦住 `fetch`、把改过的内容交出去。所以"输入框字号改回 15px""viewport 里删掉禁止缩放"这种变异也能跑。

每条的结局：

| 显示 | 意思 | 该做什么 |
|---|---|---|
| 抓到了 | 有测试变红，下面列出是哪几条 | 没事 |
| **没抓到** | 改坏了测试还是全绿 | 先确认这个改动真的造成了用户看得出的差别；没有的话是变异无效（甚至说明那段代码多余），有的话去补测试 |
| 已过期 | 原文在文件里找不到，或者出现了好几处 | 代码改过了，照新代码更新这条的 `find` |
| 跑不起来 | 改出了语法错误 | 这种"失败"不算测试的功劳，把 `replace` 写成合法代码 |
| 超时 | 一分钟没跑完 | 可能改出了死循环 |

**开始之前它会先自检两次**：代码不改时测试必须全绿；故意让应用一启动就报错时测试必须大片失败。
任何一次不对就直接停下、不给结果——这个工具要是自己坏了（比如改过的代码其实没被用上），给出的"全部抓到"就是假的。

做完这个工具时，还往清单里临时塞了五个"答案已知"的诱饵（只改注释、原文不存在、原文有 50 处、改出语法错误、改测试页没加载的 `sw.js`），五个都判对了。

**自检真的拦下过问题**：给工具加"拦截 fetch"时新写的一条测试用了 `location.href` 算目录。在普通测试页里没问题，可在工具的隐藏测试页里 `location.href` 是 `about:srcdoc`，这条测试失败了——工具的第一个自检（"不改代码应该全绿"）当场拒绝运行，没有给出任何结论。改成 `document.baseURI` 就好了。

**过期提醒也真的起作用了**：做右下角 + 按钮时删掉了列表底部的旧按钮，清单里三条变异跟着对不上，页面直接标成"已过期"。其中两条那段逻辑还在（只是写法变了），照新代码更新了 `find`；另一条的逻辑整个没了，删掉，由新功能那组里的一条接替。

**加新功能时**：写完测试后，想想"这个功能最可能怎么坏"，每种坏法往 `mutations.js` 里加一条，然后跑这一组。
从代码里原样复制 `find`（包括缩进和注释），换行写成 `\n`。

以后新增功能后，把"最可能的坏法"加进 `mutations.js`，用 `mutate.html` 跑，不用再手动改文件。

**注意变异本身也可能是无效的**：有一次我把"置顶排序"改成先全局排序再按清单过滤，测试全绿——查下来是这个改法根本没造成可观察的差异（过滤之后每个清单内部顺序还是对的），不是测试有漏洞。换成"干脆不排序"之后立刻就被抓到了。所以测试没变红时，先确认你的破坏是真的破坏。

**无效的变异有时说明代码本身是多余的。** 做清单标签时，共用组件里有个 `forgetTag()`：删标签时顺手把"正在管理哪个标签"清掉。把它删了，测试全绿。查下来确实没有任何用户能看到的差别——画操作条之前本来就要去标签列表里找这个标签，删掉的标签自然找不到。既然去掉它谁都察觉不到，它就只是多一段要读懂的代码，于是整个删了。**判断方法**：想不出任何"用户能看到的不同"来写测试时，先怀疑这段代码该不该存在，而不是硬写一条测内部变量的测试。

**但有时候真的是测试写错了**。做"今天"页时，我写了一条"这一页不能拖拽"的测试，看起来很合理：

```js
drag(items[0], ...);                                    // 拖一下
assertEqual(document.querySelector('.drag-ghost'), null);   // 检查没有浮起副本
```

变异测试发现它抓不到任何问题——因为 `drag()` 里已经包含了"松手"，而副本在松手时本来就会被移除。**这条断言永远成立，等于没写。** 正确的写法是在拖动**进行中**检查（发完 `pointermove` 就断言，先别 `pointerup`）。

这类"假测试"是最危险的：它让你以为有保障，实际什么都没测。**只有变异测试能发现它们。**

### 测试可能只是"侥幸通过"

比"假测试"更隐蔽的一种：断言写对了，但选的数据恰好碰不到 bug。

做补录时我写了一条测时区的测试，补录时间填 23:30，断言这条记录要落在选中那天。
然后故意把代码改成"把用户填的时间当成 UTC"——**这条测试居然是绿的**。

原因：本机在 UTC-7，`23:30Z` 换算回本地是当天 16:30，日期没变，所以看不出来。
换成 UTC+8 的机器，同样的 bug 立刻就会让这条测试变红。
也就是说，**这条测试能不能发现问题，取决于跑它的机器在哪个时区**——这比没有测试更糟，
因为它给了你一种虚假的安全感。

改法是凌晨和深夜各补一次，断言两次都落在同一天：

```js
backfillLog('log-喝水', '2026-09-06', '00:30');
backfillLog('log-喝水', '2026-09-06', '23:30');
assertEqual(countLogsByDay(logItems[0])['2026-09-06'], 2, '两次都该算在 9 月 6 日');
```

不管在哪个时区，这两个时间点里总有一个会跨过午夜。加强之后重跑那个变异，
报错变成了 `{"2026-09-05":1, "2026-09-06":1}`——一眼就能看出问题在哪。

**经验**：测和"边界"有关的功能（时区、月初月末、跨年、正好到点），
一个样例往往不够，要挑**边界两侧**的样例。

**第二个例子：内存里的"剩饭"帮 bug 打了掩护。**
读项目时要对照标签列表清理无效的标签 id，所以启动时必须先读标签、再读项目。
我专门写了一条"重开应用后项目身上的标签还在"的测试，然后故意把读取顺序对调——**它是绿的**。

原因：`logTags` 是全局变量，这条测试自己前面几步（甚至上一条测试）已经把同样 id 的标签留在了内存里。
读项目时对照的是这份"剩饭"，所以顺序错了也照样对得上。
可手机上真正冷启动时内存是空的，**用户所有项目的标签会在打开 App 的一瞬间全部消失**。

改法是在测试里先把内存清空（`logTags = []; logItems = [];`）再 `initApp()`，模拟真正的冷启动。

**经验**：测"启动 / 读数据"相关的逻辑时，先把内存里的数据变量清空，
否则你测到的可能是上一步留下的东西，而不是从存储里读出来的。

### 两个元素永远"相等"

做新增标签时，我写了 `assertEqual(document.activeElement, input, '光标要自动放进去')`。
变异测试把"光标放进这个输入框"的代码删掉——**测试是绿的**。

原因在测试工具本身：`assertEqual` 是把两边转成 JSON 再比，而**所有页面元素转成 JSON 都是 `{}`**。
所以拿任意两个元素去比，永远相等。光标在不在输入框里，这条断言根本看不出来。

这比某一条测试写错更严重，因为谁都可能再写出同样的代码。所以改的是工具：
**`assertEqual` 现在碰到两边都是元素时直接报错**，并提示改用 `assert(a === b, ...)`。
和 `null` 比较（"这个元素应该已经不在了"）是正常用法，不受影响。有一条自检盯着这个行为。

### iPhone 会照着页面最顶上的颜色给状态栏上色

用户截图：点 + 打开新建面板、再关掉，最上面的状态栏（时间、电量那一条）变成了灰色，和下面的白色页面有一条明显的分界。
那个灰是 `#ADADAD`——正好是遮罩的 `rgba(0, 0, 0, 0.32)` 叠在白底上算出来的颜色。
新一点的 iPhone 会参考贴在页面最顶上的固定元素给状态栏上色：遮罩盖到最顶上时状态栏被染灰；
关掉后，最顶上剩下的是上一轮新做的 `.page`，而它**没有底色（透明）**，状态栏就停在了灰色上。

修了两层：遮罩从状态栏下面开始（`top: env(safe-area-inset-top)`）；`.page` 加上白色底。两条测试各盯一层。
**预览浏览器模拟不了 iPhone 的状态栏上色，这个 bug 是否真的修好要在手机上确认。**

### 手机专用的样式，写的位置不对就不生效

把清单页做成"上面固定、下面自己滚"时，手机上顶部该留 24px，截图里却空了 60px。
原因是 CSS 的先后顺序：手机专用的 `@media (max-width: 600px) { .page { padding-top: … } }` 写在了文件开头，
而电脑用的 `.page { padding-top: 60px }` 写在后面——两条一样"具体"时，**写在后面的赢**，手机专用的那条等于没写。

所有测试都是绿的，因为测试页是电脑宽度，这条规则本来就不该生效。是手机尺寸的截图看出来的。
补了一条测试：开一个 375px 宽的小窗口，套上 App 的样式去量（`tests-mobile.js` 的 `styleAtWidth()`）。

### 拖拽测试要"一路挪过去"，别"一步跳过去"

"拖着经过收起的清单时，占位行会出现在它下面"这条测试，单独跑是绿的，整套一起跑就红。
在失败信息里带上坐标之后看到：先量好目标清单的位置、再一步把指针移过去，**中间目标往上挪了 55px**，指针落在了它下面。
具体是什么让它挪的，单独重放没能复现，没有查到底；但这个写法本身就脆——真的手指是一路挪过去的。
改成先挪一小段让拖动开始，再量目标当前的位置、移过去。失败信息里的坐标留着，下次再出问题能直接看到数字。

### 窗口没有焦点时，focus 事件不会发

做"打字时收起标签栏"时，两条测试死活过不了：`input.blur()` 之后 `typing` 还在。
查下来是**测试页所在的浏览器窗口没有焦点**（开着测试页、人在别的窗口，`document.hasFocus()` 是 `false`）。
这时 `.focus()` / `.blur()` 只会改 `document.activeElement`，**不发 `focusin` / `focusout` 事件**——而代码正是靠这两个事件工作的。手机上真实使用时一定会发。

所以那两条测试按真实浏览器的顺序自己补发事件（`tests-mobile.js` 的 `focusField()` / `leaveField()`）。
窗口有焦点时浏览器也会发一遍，处理函数重复跑两次结果一样，不影响。

### 听事件时，挂的位置决定了你看到的是"改之前"还是"改之后"

想测"从一个输入框跳到另一个时，`typing` 一直都在"，第一版把记录函数挂在 `root` 上。
可事件是从里往外传的：`root` 上的处理会比 `app.js` 挂在 `document` 上的处理**先跑**，那时 `typing` 还没被动过，永远是 `true`——**这条测试永远不会失败**。
写完回头检查时发现的，改成挂在 `window` 上（在 `document` 之后）。

### 测试自己把光标放进了输入框，结果被"打字时不算"挡住

做详情页返回手势时，"打卡详情页也能滑回去"这条一直是红的。它先打开了改名框（想顺便验证返回时把改名状态收掉），可 `render()` 会把光标放进新出现的输入框——而"正在打字时不返回"正是刚定下的规则。代码是对的，是测试的准备步骤碰到了另一条规则。
改成打开改名框后先 `blur()`，只留着"正在改名"的状态。**经验**：新规则会挡住某些情况时，回头看看测试的准备步骤有没有无意中踩进这些情况。

### iPhone 上没有 dblclick，自己数两次点击的间隔

"双击标题回到今天"第一版用的是浏览器自带的 `dblclick` 事件。电脑上的测试全绿，**装进模拟器里一点反应都没有**——
iPhone 上双击是系统手势（缩放、选词），这个事件经常根本不发。改成自己记上一次点击的时间、间隔在 300ms 内就算连点两下，
电脑的鼠标双击也照样认。
**经验**：跟手势沾边的浏览器事件（`dblclick`、`contextmenu` 这类），在壳里都要亲手点一遍再信。

### 变异改的常量，测试不能跟着引用

上面那条的配套测试是"两下点得太慢不算"，等待时间原本写成 `sleep(DOUBLE_TAP_GAP + 80)`——很干净，但
变异测试把这个常量改成 100000 之后，**测试自己睡了 100 秒**，结局从"抓到了"变成"超时"。
现在那里写死 380ms，并在常量旁边注明"改这里记得改那边"（成对的魔数）。
**经验**：测试里的等待时间别引用被测代码里的常量，变异一改就把自己绕进去了。

### 断言看的是"位置"，而不是真实数据

日历周视图那条测试，原来是看七个格子上写的是不是"一二三四五六日"。看着挺合理——
可那七个字当初就是**按格子排第几个**写上去的（`WEEKDAYS[index]`），日期哪怕排错了，字也照样对。
把"周一开头"故意改坏，测试全绿。变异测试抓到之后做了两件事：
**代码改成按这一天真正是星期几来写名字**，**测试改成检查每格的真实日期**（第一格 `getDay()` 得是 1、七天要连着、里面得有今天）。

### 日期字符串再丢进 new Date() 会倒退一天

做日历页时，月历上点一下「上个月」直接翻过去**两个月**。
原因：`'2026-08-01'` 这种只有日期没有时间的字符串，`new Date()` 会当成 **UTC 零点**；
在比 UTC 慢的时区（这台机器是 UTC-7）换算回本地日期就成了 7 月 31 日，月份自然退了一格。
项目里早就记着「别从 ISO 字符串截前 10 位当本地日期」，这次是**反方向的同一个坑**：
已经是本地日期的字符串，别再丢回 `Date` 里转一圈。
现在 `dateKey()` 认出这种字符串就原样返回，并且有一条测试钉着（`tests-calendar.js` 里那条「日期换算不会被时区带偏」）。

### 手势改了方向，变异清单要跟着重来一遍

先做的是"详情页往下拉返回"，用户用下来觉得不顺，改成了"手指往右滑返回"（大家更习惯这个方向）。跟着要改的不只是代码和测试：**变异清单里有两条失去意义了**——"页面往下翻过了还返回"这条，改成左右滑之后翻到哪儿都该能返回，于是反过来加了一条"翻过之后就返回不了了"；"列表页往下拉也被拦"这条，改成左右滑之后列表页本来就有左右滑切换标签，把它去掉没有任何可观察的差别，**删掉**。
**经验**：变异只有在"改坏之后用户看得出差别"时才有意义。改了交互方向，先把这一组每条重新读一遍，别留着看起来还在、其实什么都没验证的条目（留着会变成"没抓到"，或者更糟：抓到的是别的东西）。

### 只在松手之后检查，查不到"滑的过程中"出的问题

当时还是"往下拉返回"，"列表页往下拉什么都不发生"第一版是滑完、松手、再检查"没拦滚动"。可松手后本来就不会拦——**这条断言恒成立**。真正要防的是"列表页上往下拉时把滚动拦了（列表往上翻不动）"，这只在手指还没松开时看得到。写变异时对着这条想了一下才发现，改成挪完先检查、再松手。和"今天页不能拖拽"那条假测试是同一种错（见 skill 的 testing.md ①）。

### 规则变了、测试跟着改时，别让它悄悄变弱

把右下角 + 从"新建清单"改成"新建任务"后，"重开应用时面板状态清掉"那条测试只把按钮文字改了，
实际上**新建清单面板在这条测试里再也没被打开过**——"它的状态是空的"本来就成立，查了等于没查。
变异工具里"重置时漏掉新建清单的面板"那条立刻变成了"没抓到"。改成三个面板都真的打开一遍，才又抓到。

**经验**：改老测试时，确认它原本要验证的那件事，改完还真的在发生。

### 测试页自己的样式会干扰量出来的位置

测 + 按钮和"撤销"提示的位置时，量出来提示压在按钮上 8px，看着像是 bug。
查下来是 `test.html` 自己写了 `button { margin-bottom: 20px }`——+ 按钮也是个 `<button>`，被它往上顶了 20px。手机上根本没有这条规则。

所以要看真实样式的测试（`tests-mobile.js` 的 `useAppStyles()`）**加载 `style.css` 的同时，把测试页自己的样式临时关掉**，测完再打开。
**经验**：测"长什么样、在哪里"时，确认量的环境和真实环境一样。

## 测试之间不能互相影响

跑两遍测试，两遍结果必须一样。如果第二遍开始出现莫名其妙的失败，通常是某条测试改了全局状态却没还原。

已经踩过的两个：

- `currentTab`（当前在哪个标签页）没被 `resetViewState()` 重置，导致"今天"页的测试跑完后，后面所有测试都在错误的页面上运行
- `suppressNextClick`（拖动后忽略一次点击的标记）在拖拽中途失败时被留成 `true`，把下一条测试的第一次点击吞掉了

两个都是在 `app.js` 的 `resetViewState()` 里补上重置解决的。打卡模块的界面状态放在 `logs.js` 的 `resetLogViewState()` 里，由 `resetViewState()` 统一调用。

**现在这件事已经自动化了**：运行器每次都连跑两遍并比对结果，不一致就报警。
所以这类问题以后会自己冒出来，不用再靠碰巧发现。

**但有一种情况不会出现"不稳定"警告**：如果上一轮已经把状态弄脏了，两遍会一模一样地失败。
打卡模块做变异测试时就碰到了——漏了重置详情页状态，结果是 93 条测试一起挂，而不是黄色警告。
所以**看到几十条毫不相干的测试同时失败，第一反应也应该是状态泄漏**，而不是去一条条查。

新增全局状态变量时，记得问一句：**它需要在 `resetViewState()`（或 `resetLogViewState()`）里重置吗？**
凡是"界面当前处于什么状态"的变量，答案基本都是要。
