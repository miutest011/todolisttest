# 测试怎么写、变异测试怎么做

配合 `SKILL.md` 第 3、4 步使用。已有的测试写了什么、做过哪些变异，
在 `tools/README.md` 里；这里讲的是**方法**。

## 怎么跑

```bash
python3 tools/dev-server.py
```

打开 http://localhost:4173/tools/test.html。改完代码点"重新运行"，不用刷新页面。

**一定要用这个脚本，不要用 `python3 -m http.server`。** 自带的那个不发缓存头，
浏览器会自作主张缓存，你改完代码看到的还是旧版本。这个坑连续踩过四次才找到根源。

顶部汇总栏里有四种信号，**黄色警告和红色失败一样严重**：

| 显示 | 含义 |
|---|---|
| 全部通过 N 条（已连跑两遍） | 及格线，不是终点 |
| N 条失败 | 下面列出期望值 / 实际值 |
| N 条结果不稳定 | 测试之间有状态泄漏，两遍结果不一致 |
| N 条没有断言 | 假测试，什么都没验证 |
| 跳过 N 条 | 当前环境跑不了（双击打开时读不了项目文件），换服务器打开就会跑 |

## 一条测试长什么样

三段式：准备环境 → 操作 → 检查。

```js
test('这个功能应该怎样', () => {
  setup({ categories: ['工作'] });                  // 干净的假数据环境
  addTodo('工作', '写周报');                        // 操作
  assertEqual(todos.length, 1, '应该有一条任务');    // 检查
});
```

`setup(data)` 会把所有外部依赖换成假的、把时间冻在 `FIXED_NOW`、跑完自动清理，
返回 `{ root, storage, notifications, blobs }`。附件相关的写成 `async`。

几条容易忘的：

- **每次点击都会整个重画，之前拿到的元素引用作废了。** 每一步操作之后重新从 `root` 查。
- **比较对象时用 `pick(todo, ['text', 'status'])` 只挑关心的字段。** 直接比整个对象的话，
  以后每加一个字段这条断言都会误报一次。已经踩过。
- 需要模拟操作时用 `click()` / `press()` / `typeInto()` / `drag()`，别自己拼事件。
- 测提醒不要真等，用 `isoAfter(分钟数)` 造时间再调 `checkReminders()`。

## 每个功能测哪些

至少三层，缺一层就有整类问题漏出去：

1. **数据层**：字段存对了没、存进 storage 了没、边界情况（空输入、重名）挡住了没
2. **渲染层**：界面上该出现的出现了没、不该出现的没出现、分组和排序对不对
3. **点击层**：点了之后发生什么，以及**不该发生什么**

第三层里"不该发生什么"最值钱，因为手机上的问题几乎全是这一类：
点勾选框不该跳详情页、点数字不该跳详情页、拖完之后那次点击不该被当成点击、
"今天"页不该能拖拽。这些每一条都对应一次真实的误触投诉。

**修 bug 的时候顺手补一条测试**，同一个 bug 就不会回来第二次。

## 变异测试：验证测试本身有没有用

全绿不能证明测试有用。**故意把代码改坏，看测试会不会红**，这才能证明。

做法：改完功能之后，想想这个功能最可能怎么坏，每种坏法往 `tools/mutations.js` 里加一条
（`group` / `name` / `file` / `find` / `replace`，`find` 从代码里原样复制、必须正好出现一次），
然后打开 `tools/mutate.html` 选这一组跑。结局怎么看、每种结局该怎么办，页面上和 `tools/README.md` 里都写了。

**`name` 写成"bug 长什么样"**（"删标签时不从项目身上去掉"），而不是"删了第 280 行"——
代码会变，bug 的样子不会变，过期了也知道这条原本想验证什么。

### 挑哪些地方改

挑**真实的 bug 会长什么样**，不是随便乱改。经验上最容易出问题的几类：

| 类型 | 具体改法 |
|---|---|
| 忘了保存 | 把 `saveTodos()` 注释掉 |
| 忘了 `stopPropagation` | 删掉嵌套点击里的那一句 |
| 边界差一位 | 插入位置 `index` 改成 `index + 1` |
| 正负号反了 | 提醒的"提前"算成"延后" |
| 顺序 / 分组规则 | 干脆不排序、默认展开而不是收起 |
| 状态没重置 | 从 `resetViewState()` 里删掉一个变量 |
| 连带清理漏了 | 删任务时不删它的附件文件 |
| 组件契约破坏 | 丢掉 `buttonClass` 参数、返回值类型改掉 |

### 测试没变红时怎么办

**先确认你的破坏是真的破坏。** 有一次把"置顶排序"改成先全局排序再按清单过滤，
测试全绿——查下来是这个改法根本没造成可观察的差异（过滤之后每个清单内部顺序还是对的）。
换成"干脆不排序"立刻就被抓到。所以第一反应是检查变异本身，不是急着补测试。

**确认没有任何可观察差异时，问一句：这段代码该不该存在？** 共用标签组件里有个 `forgetTag()`，
删标签时清掉"正在管理哪个标签"。变异把它删了，测试全绿——因为界面画操作条前本来就要去列表里找这个标签，
找不到就不画。用户永远看不出区别，那它就只是多一段要读懂的代码，于是删掉了。
别为了让变异变红去硬写一条"测内部变量"的测试。

确认破坏是真的，测试还是绿的，那就是测试有漏洞——按下面几类去找。

**全绿的第一次运行最值得怀疑。** 标签功能新写的 30 条测试一次全绿，变异测试随后挖出了两条侥幸通过和一个工具盲区。

### "已过期"的变异

代码改过之后，有些变异的 `find` 会对不上。这不是测试的问题，但**别直接删**：
先看看那段逻辑还在不在。还在（只是写法变了），就照新代码更新 `find`——那个 bug 照样可能发生；
逻辑整个没了，才删掉这一条。

### 工具本身也要能被验证

`mutate.html` 是用来检验测试的，它要是自己算错了，所有结论都是假的。所以：
它的小函数有 `tests-mutate.js` 盯着；它自己也在 `mutations.js` 的"测试工具"组里被变异；
每次运行前还有两个自检（不改应该全绿、弄坏应用应该大片失败）。
做它的时候还用了**诱饵**：临时塞几条答案已知的变异（只改注释→没抓到、原文不存在→已过期、语法错误→跑不起来……），全部判对才算数。

## 六种坏测试

### ① 假测试：断言永远成立

最危险的一种，它让你以为有保障，实际什么都没测。

做"今天"页时写过一条"这一页不能拖拽"：

```js
drag(items[0], ...);                                       // 拖一下
assertEqual(document.querySelector('.drag-ghost'), null);  // 检查没有浮起副本
```

看着完全合理，但 `drag()` 里已经包含了"松手"，而副本在松手时本来就会被移除——
**这条断言在任何情况下都成立**。正确写法是在拖动**进行中**检查：发完 `pointermove` 就断言，
先别 `pointerup`。

运行器会把一次断言都没做的测试标黄，但这种"有断言、但断言恒真"的**只有变异测试能发现**。

### ② 侥幸通过：断言对了，但数据恰好碰不到 bug

比假测试更隐蔽。做补录时写过一条时区测试，填 23:30，断言记录落在选中那天。
然后故意把代码改成"把用户填的时间当成 UTC"——**这条测试居然是绿的**。

原因：本机在 UTC-7，`23:30Z` 换回本地是当天 16:30，日期没变。
换台 UTC+8 的机器，同样的 bug 立刻就会让它变红。也就是说
**这条测试能不能发现问题取决于跑它的机器在哪个时区**，比没有测试更糟。

改法是取边界两侧：

```js
backfillLog('log-喝水', '2026-09-06', '00:30');
backfillLog('log-喝水', '2026-09-06', '23:30');
assertEqual(countLogsByDay(logItems[0])['2026-09-06'], 2, '两次都该算在 9 月 6 日');
```

不管在哪个时区，这两个时间点里总有一个会跨过午夜。

**规律**：测边界相关的功能（时区、月初月末、跨年、正好到点、列表头尾），
一个样例基本不够，要挑边界**两侧**。

**另一种侥幸：内存里的"剩饭"。** 启动时必须先读标签再读项目（读项目要对照标签清理无效 id）。
专门测这件事的测试，在读取顺序被故意对调后**还是绿的**——因为全局变量 `logTags`
里留着前面几步读进来的同一批标签，对照的是剩饭，而不是存储。手机冷启动时内存是空的，
用户的标签会全部消失。

**规律**：测启动、读数据相关的逻辑时，先把数据变量清空（`logTags = []; logItems = [];`）再 `initApp()`。

### ③ 状态泄漏：测试之间互相影响

运行器每次连跑两遍并比对，不一致就报黄条，所以这类问题现在会自己冒出来。

**但有一种情况不会报黄**：如果状态在上一轮就被弄脏了，两遍会一模一样地失败。
打卡模块漏了重置详情页状态时，结果是 93 条测试一起挂，而不是黄色警告。

所以——**看到几十条毫不相干的测试同时失败，第一反应是找状态泄漏，别一条条查。**

### ④ 断言工具本身有盲区

`assertEqual` 用 JSON 比较，**所有页面元素转成 JSON 都是 `{}`**，所以
`assertEqual(document.activeElement, input)` 永远通过——光标在哪都一样。

运行器现在会拦下"两边都是元素"的 `assertEqual` 并报错。**比较元素一律用 `assert(a === b, ...)`**；
和 `null` 比（"这个元素应该不在了"）照常用 `assertEqual`。

**规律**：变异测试没抓到时，除了怀疑变异和测试，**也要怀疑断言函数本身**。
找到工具的盲区，修工具，别只修那一条测试——下一个写测试的人会掉进同一个坑。

### ⑤ 测试环境和真实环境不一样

- **浏览器窗口没焦点时，`.focus()` / `.blur()` 不发 `focusin` / `focusout`。** 测试页常常在后台跑，靠这两个事件工作的代码要在测试里手动补发（`tests-mobile.js` 的 `focusField()` / `leaveField()`）。
- **测试页自己的样式会干扰 App 元素**（`button { margin-bottom }`），量位置前先关掉，见下面"测长什么样、在哪里"。
- **听事件时挂的位置很关键**：挂在 `root` 上会比 `app.js` 挂在 `document` 上的处理先跑，看到的是"改之前"的状态。想看处理完的结果，挂在 `window` 上。

### ⑥ 改老测试时悄悄变弱

规则变了要改老测试，但**要确认它原本想验证的事改完还在发生**。
例子：+ 从新建清单改成新建任务后，"重开应用清掉面板状态"只改了按钮文字，新建清单面板在测试里再也没打开过，
"它的状态是空的"变成恒真。变异测试立刻把它揪了出来。

## 自动测试测的是我们的逻辑，不是平台的行为

测试里的事件是测试自己造的：`dispatchEvent(new MouseEvent('dblclick'))`。
这能验证"收到这个事件之后代码做得对不对"，**验证不了"真手指会不会产生这个事件"**。
后者是假设，而假设错了的时候，测试照样全绿——"双击回到今天"就是这么过的关，装进 iPhone 一点反应都没有。

**判断方法**：一条测试里如果出现"我先造一个事件"，那它就依赖一个平台假设。
把这个假设写进 `tools/platform.html`，到真设备上点一遍确认，别让它只活在脑子里。

顺带：**跑在哪个引擎上也是假设**。日常跑的是 Chromium，手机是 WebKit，
所以改完和手机有关的东西，把同一套测试搬进模拟器的 Safari 再跑一遍（命令见 `tools/README.md`）。

## 假依赖要装在 `setup()` 之后

`setup()` 会把所有可替换的依赖复位成"网页版的样子"（假存储、假时间、假通知、没人接手的提醒、默认的存文件/选文件）。
所以测试里装自己的假货，必须排在 `setup()` 后面 —— 装早了会被它冲掉，而现象是"一条都没交出去"，
看起来像功能没做，其实是测试顺序不对（真踩过，一次挂了 8 条）。

复位这件事本身值得写进 `setup()`，而不是靠每条测试自己收尾：忘了收尾的那条会悄悄影响后面所有测试，
这种问题查起来最费劲。

## 测"长什么样、在哪里"

**手机专用的样式（`@media (max-width: …)`）在测试页里量不出来**：测试页是电脑宽度，那些规则本来就不生效。
要开一个手机那么宽的小窗口，把 App 的样式放进去量——`tests-mobile.js` 里的 `styleAtWidth(宽度, html, 选择器)`。

**滑动手势的测试同理**（`tests-gestures.js` 的 `fingerSwipe()`）：分几步挪，方向是在走过阈值的那一步定的；"滑的过程中该不该拦滚动、页面有没有跟着手指走"要在**松手之前**检查，松手之后这些本来就复原了，查了等于没查。

**拖拽测试要像真的手指一样一路挪过去**：先挪一小段让拖动开始，再量目标现在在哪、移过去。
先量好位置再一步跳过去，中间页面动一下指针就落空了（真踩过，整套一起跑时才出现）。失败信息里带上坐标，出问题时直接能看到数字。

测试页平时不加载 `style.css`，所以位置、字号、`touch-action` 这类检查要用 `tests-mobile.js` 里的 `useAppStyles()`：
它临时加载 App 的样式，**同时关掉测试页自己的样式**（`test.html` 有 `button { margin-bottom: 20px }`，会把 App 的按钮顶偏，量出假 bug）。

断言位置时挑**和屏幕宽度无关**的关系："撤销提示的底边在按钮顶边之上"比"两者不重叠"可靠——
测试页窗口很宽时两者本来就左右隔得远，"不重叠"会侥幸通过。

`mutate.html` 也能改 `style.css`、`index.html`，所以这类样式契约同样可以做变异测试。

## 运行器本身也要能被信任

`tools/tests.js` 末尾有 7 条自检，包括"断言函数坏了会不会被发现"
"异步测试的失败会不会被悄悄吞掉"（运行器漏一个 `await`，所有 `async` 测试都会假装全绿）。

改动 `test-runner.js` 时，这几条一定要还在、还得跑。
测试工具自己失灵是最坏的情况：它会让所有测试同时变成谎话。

## 什么时候用 skip

只用在"这个环境根本没法检查"——比如要读项目文件，双击打开测试页时浏览器不让读。
`skip('原因')` 会显示成灰色，不算失败，也不会被当成假测试。

**别用 skip 绕开真正的失败。**
