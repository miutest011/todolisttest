# 代码怎么组织、怎么写

配合 `SKILL.md` 第 2 步使用。这里讲的是**约定**，不是现状清单——现状看 `README.md`。

## 文件分工

```
index.html   只有骨架：几个 <script> 加一句 initApp()。逻辑一行都不放
style.css    全部样式，开头是 :root 设计变量
app.js       待办清单：清单 / 今天 / 详情页 / 提醒 / 附件 / 拖拽 / 通用组件
tags.js      标签界面（顶部标签行、长按管理、点选），清单页和打卡页共用
logs.js      打卡：独立的一块数据和界面，借用 app.js 和 tags.js 的通用组件
sw.js        离线缓存
tools/       测试工具（自成一套，见 tools/README.md）
```

**新加脚本文件要同时改三个地方**：`index.html` 的 `<script>`、`sw.js` 的 `FILES`、
`tools/test.html` 的 `SCRIPTS`。漏第二个会导致离线时缺文件（有测试盯着），
漏第三个会导致**里面的测试根本不跑，而且没有任何报错**——这是最阴的一种。

功能大到什么程度该拆新文件？打卡是个好标尺：它有自己的数据、自己的页面、
和待办几乎没有交集。反过来说，"今天"页只是待办数据的另一种展示，就留在 `app.js` 里。

## 状态驱动渲染

整个界面只有一条路径：**改状态变量 → 调 `render()` → 整个界面重画**。

```js
function addTodo(category, text) {
  todos.push({ ... });   // 1. 改数据
  saveTodos();           // 2. 存起来
  render();              // 3. 重画
}
```

不要手动去改某个 DOM 节点的文字或 class。看起来省事，实际是这类应用最大的 bug 来源：
界面和数据会慢慢对不上，而且对不上的时候你查不出来。整个重画很快，这点性能不用省。

**直接后果**：每次点击之后，之前拿到的元素引用就作废了。写测试时尤其容易踩，
见 `pitfalls.md`。

## 外部依赖都要能替换

凡是"浏览器提供的、测试里不好用的"东西，都在 `app.js` 顶部做成变量 + 一个 `useXxx()` 设置函数：

| 变量 | 真实环境 | 测试里换成 |
|---|---|---|
| `storage` | `localStorage` | 内存假存储 |
| `confirmFn` | `window.confirm` | 直接返回 true |
| `nowFn` | `() => new Date()` | 冻结在 `FIXED_NOW` |
| `notifier` | 系统通知 | 记进数组 |
| `blobStore` | IndexedDB | 内存 Map |
| 长按判定时长 | 500ms | 0 |
| 撤销提示时长 | 4000ms | 每条测试还原 |

```js
let storage = window.localStorage;
function useStorage(fake) { storage = fake; }
```

**加新的外部依赖时照这个模式做，不要直接写 `window.xxx`。** 否则那块功能就永远测不了，
或者测试会真的弹窗、真的写你硬盘。判断标准很简单：这东西在测试里会不会不受控？
时间、随机数、网络、弹窗、通知、文件、定时器，答案都是会。

## 界面状态必须能重置

`resetViewState()`（`app.js`）负责把"界面现在处于什么状态"的变量全部清零，
打卡模块的那部分在 `logs.js` 的 `resetLogViewState()` 里，由前者统一调用。

**新增一个全局变量时，问一句：它需要进重置函数吗？**
凡是回答"界面当前处于什么状态"的——在哪个标签页、展开着哪个菜单、正在编辑哪一条、
翻到了哪个月、选中了哪一天——答案都是要。

漏掉的代价是真金白银：漏 `currentTab` 让后面所有测试跑在错误的页面上；
漏打卡详情页的状态直接导致 93 条测试一起挂。运行器现在会连跑两遍自动抓这类问题，
但**前提是你把变量放对了地方**。

## 通用组件

已经抽出来的：

- `createPageHeader(onBack, menu)` — 详情页顶部那一行：左边悬浮圆形返回键（SVG 箭头），
  右边可选的悬浮圆形 ⋯ 菜单。待办详情页和打卡详情页共用。新页面要顶部就用它，别自己写。
- `createMenu(key, items, buttonClass)` — ⋯ 菜单。`key` 用来记住"当前展开的是哪个菜单"，
  `items` 是 `{ label, onClick }` 数组，`buttonClass` 传 `'round-btn'` 就是悬浮圆形款。
- `createIcon(name, className)` — 从 `ICON_PATHS` 取 SVG 路径画图标。
- **`tags.js` 里的标签界面** — `createTagBar(set)`（顶部"所有 | 标签… | 已归档 | + 新增"加长按管理条）、
  `createTagPicker(set, …)`（可点选的一排标签）、`onLongPress(element, callback)`。
  清单页和打卡页各传一个"标签集"进去（`listTagSet` / `logTagSet`），说明自己的标签数组、筛选状态、增删改函数。
  **界面状态（`addingTagIn` / `managingTagId` / `renamingTagId`）两页共用**，换底部页面时要收起。
  第三个页面要标签时，照着这两个标签集再写一个，别复制界面代码。
- 菜单项支持 `checked: true`（右边打勾），用于"放到标签"这种单选。
- `createTodoItem(todo, index, { draggable, pinnable })` — 同一条任务在不同页面上长得不完全一样：
  "今天"页混着不同清单的任务，传 `draggable: false, pinnable: false`（没有顺序可言、置顶说不清在哪置顶）。
  **一个按钮放在某个页面上会让人分不清它作用在哪时，就别在那个页面放。**
- `trackSwipe(target, { canStart, canLock, onMove, onRelease })` — 手指左右滑手势的公共部分：只认手指、走过 `MOVE_THRESHOLD` 才定方向（左右为主才归它）、定了就不改、归我们的那一下拦住页面滚动、松手时算"滑得够远 / 甩得够快"。详情页往右滑返回（挂在 `document` 上，因为详情页内容短时下面的空白不属于它）和列表区左右滑切换标签（`tags.js` 的 `enableTagSwipe(scroller, set)`，挂在 `.page-scroll` 上）都用它。什么时候不算手势统一在 `canStartSwipe()`：按在输入框里、正在打字、菜单开着。**再加手势就用它，别再写一套按下 / 移动 / 松手。**
- `createFab(label, onClick)` — 右下角浮着的蓝色圆形 + 按钮。`label` 给读屏软件用。页面上放了它，记得给这一页的容器加 `has-fab`（列表底部留空）。
- `createDueButton(dueAt, remindBefore, onClick)` / `createDueEditor(dueAt, remindBefore, { onSave, onCancel, onClear })` — 闹钟和它下面的设置区。
  **只管显示和收集输入，不管存到哪**：详情页存到任务上（`setDue`），新建任务面板存到草稿里，加任务时再带上。
  一开始它们直接读写 `todos[index]`，要在还没有任务的新建面板里用时才改成这样——**组件要被第二个地方用的时候，先把"存到哪"拆出去**。
  填的值怎么换算成数据统一走 `parseDueInput()`，免得两处算得不一样。
- `createPopupCard({ title, body, onSubmit, onCancel })` — 新建面板的"壳"：暗色遮罩 + 靠上方的卡片 + 取消/创建。
  卡片里放什么由各页决定（清单：名字 + 单选标签；打卡：名字 + 多选标签）。**壳共用、内容各管各的**，这是判断"要不要抽组件"的好标准。
  面板里的输入框要边打字边把内容记进草稿（`input` 事件），因为点面板里的标签会整页重画。

**两页先各写一份、第二次用到时再抽出来**，这次标签就是这么做的：打卡先做完、测试齐了，
做清单时才抽成 `tags.js`。先抽象再使用的话，往往猜错哪些地方需要可变。
抽的时候，已有的那 30 多条测试就是安全网——只需要改测试里的 class 名和变量名，行为断言一条不动。

**抽公共组件时有两个固定动作**：

1. 抽完之后回头检查每个调用点，特别是**函数结尾的 `return`**。
   有过一次把菜单内容抽成 `todoMenuItems(index)`，结尾还留着 `return createMenu(...)`，
   10 条测试当场报 `items.forEach is not a function`。
2. 给组件写"它长什么样"的测试，不是"它在不在"。只断言 `.menu-btn` 存在的话，
   "忘了套圆形样式"这种问题一点都抓不到。要把 `.round-btn`、里面有没有 `svg`、
   **旧位置是不是真的挪走了**（卡片里不该还留一个）都断言上，组件的约定才算守住。

## 图标

SVG 路径存在 `app.js` 的 `ICON_PATHS` 里，用 `currentColor` 描边，颜色靠 CSS 控制。
要新图标就去 [Lucide](https://lucide.dev) / [Feather](https://feathericons.com) 复制一段 `d="..."`。
它们规格一致（24×24、只描边、圆头圆角），混用不会打架。

**不要用 emoji 当功能图标。** 各平台长得不一样、大小对不齐、颜色也没法跟着主题走。
置顶按钮从 📌 改成灰色 SVG 箭头就是为了这个。

## 样式

**所有颜色、字号、间距、圆角都在 `style.css` 开头的 `:root` 里**，下面的规则不写具体数值。

几条硬约定：

- 间距只用 4 的倍数（`--space-1` ~ `--space-7`）
- 字号只有 6 档，灰色只有 5 档（标题 / 正文 / 次要 / 说明 / 极淡）
- 需要区分手机和电脑时用 `@media (hover: hover)` / `(hover: none)`，
  不要用屏幕宽度猜——**手机上没有 hover 状态**，只靠宽度判断会把平板和触屏笔记本弄错

界面"看起来没设计感"，通常不是缺什么效果，而是这些细节不成体系。
收敛之前这个文件里散着 23 个颜色，其中一半是肉眼分不出的灰。

**成对出现的数值要互相注释。** 比如月历格子 26px 和外面的手写圈 36px 必须一起改，
就在两处都写清楚"改这个要同时改那个"。这种隐性关联不写下来，三个月后一定会改坏一个。

## 数据结构

- **认 id，不认名字和下标。** 打卡项目用 `id`，所以改名不需要到处同步。
  待办目前还在用清单名做关联，代价就是每次改名都得连带更新任务归属和折叠状态记录
  （有专门的测试盯着这件事）。**新数据一律带 id。**
  清单的"放在哪个标签下、有没有归档"（`categoryMeta`）因为清单本身没 id，只能也按名字记，
  所以清单改名 / 删除时要同步的地方又多了一处。**清单改用 id 是欠下的技术债**，适合单独找一次来还，别和新功能混着做。
- **有依赖关系的数据，读取顺序要对。** 读项目时要对照标签清理无效 id，所以必须先读标签。
  顺序反了，测试里常常看不出来（内存里残留着上一步的标签），手机冷启动时却会清空用户所有标签。
- **状态用字符串枚举，不用布尔。** 任务是 `status: 'active' | 'done' | 'abandoned'`。
  原来的 `done: true/false` 在加"已放弃"时就撑不住了。
- **迁移老数据时要把老字段删掉。** 从 `done` 迁到 `status` 时如果两个字段都留着，
  早晚会对不上，而且是那种查半天的 bug。迁移逻辑放在读取数据的地方，
  并且**补一条测试喂它老格式的数据**。
- **日期分桶一律用本地时间**，绝不用 `iso.slice(0, 10)`。理由见 `pitfalls.md`，
  这个 bug 真实发生过。
