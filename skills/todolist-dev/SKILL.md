# 待办清单项目的开发方法

这是给自己看的作业指导书。项目主人是**编程零基础**的个人开发者，项目能一路做到今天
（两百多条测试、装在 iPhone 上天天用），靠的不是写得快，而是下面这套节奏。
跳步骤的代价基本都是当场就到——最贵的一次是漏了一个状态没重置，93 条测试一起挂。

## 三条不能动的约束

**① 零依赖。** 不引入框架、构建工具、npm 包、CDN 脚本。用户最初的原话是"我要能看懂每一行"。
这不是洁癖：正因为没有依赖，用户才敢自己翻代码、才能看懂你的每个改动，
也才有了那套"浏览器打开就能跑"的测试工具。想引入什么之前，先想有没有 20 行原生代码的写法。
唯一例外是从 Lucide / Feather 复制 SVG 路径这种"抄一段数据"，不算依赖。

**② 注释写"为什么"，不写"这行干什么"。** 中文。代码本身能说清做了什么，
说不清的是当初为什么这么选。反面例子是 `// 遍历任务列表`，正面例子是
`// 本地开发时用网络优先：不这么做，你改完代码刷新看到的还是旧版本，这个坑踩过好几次`。
每一条这样的注释都是在替未来的自己省一个下午。

**③ 每个功能都配测试，而且要反过来验证测试本身。** 见流程第 4 步。这条是整个项目的地基：
用户敢做"两态改三态""420 行 CSS 收敛""加底部标签栏"这种大改动，全靠跑一遍全绿才敢按保存。

## 加一个功能，走这七步

### 1. 复杂功能先讲人话，再动手

用户说过："先别写代码。用大白话告诉我你打算怎么做、文件怎么组织，我确认后再动手。"

判断标准：要动多个文件、要改数据结构、要引入新概念 → 先讲方案，等确认。
改个颜色、挪个图标、修个小 bug → 直接做。

讲方案时**不要把技术选型摆出来让用户选**（他没有依据可选），要给一个推荐方案加上为什么。
需要用户拍板的只有产品问题："已完成的任务是沉底还是直接收起来？"这种他答得上来。

### 2. 写功能

按 `references/architecture.md` 的约定写。核心就三件事：
状态变量 → 改状态 → 调 `render()` 重画；外部依赖走可替换的注入口；新的界面状态记得进重置函数。

### 3. 补测试

每个功能至少覆盖三层：**数据对不对**（存进去的字段）、**渲染对不对**（界面上出现了什么）、
**点击对不对**（点了之后发生什么、以及**不该**发生什么）。

用户在手机上实测暴露的问题，一定要单独留一条测试钉死。
"点文字不该变成改名"就是这么来的——这类问题会反复回来，除非有测试挡着。

写法见 `references/testing.md`。

### 4. 跑测试，然后做变异测试 ← 最容易跳过，也最不能跳

```bash
python3 tools/dev-server.py
```

然后打开 http://localhost:4173/tools/test.html

全绿只是及格线。**全绿不能证明测试有用**——一条什么都没验证的测试也是绿的。
所以接着做变异测试：**把刚写的功能最可能的几种坏法加进 `tools/mutations.js`，打开 http://localhost:4173/tools/mutate.html 跑这一组，确认每条都是"抓到了"。**
它只在内存里改代码，项目文件不会动；开始前会自检，自检不过就不给结果。

这一步至今抓出过三类真问题：真实的 bug（漏了 `data-index`，拖拽静默不保存）、
假测试（断言永远成立）、状态泄漏（`currentTab` 没重置）。它不是走过场。

测试没变红时，先怀疑自己的破坏不够狠（有过一次改动根本没造成可观察差异），
再怀疑测试有漏洞。具体怎么挑变异点、怎么判断，见 `references/testing.md`。

### 5. 更新文档

- 新踩的坑、新加的测试、新做的变异 → `tools/README.md`
- 用户能感知的变化（新功能、新操作方式、新的外观约定）→ 根目录 `README.md`

这两个文件是项目的记忆。写的时候当成写给三个月后的自己看。

### 6. 收尾三件事

- **改了任何代码 → `sw.js` 里 `VERSION` 加一**，否则手机上永远是旧版本。
  （用户可能会说"这次不用加"，听他的。）
- **加了新脚本 → 同时加进 `sw.js` 的 `FILES`**。有一条测试盯着，漏了会报红。
- **清掉测试数据**。在页面控制台跑：
  ```js
  localStorage.clear(); indexedDB.deleteDatabase('todolist-files'); location.reload();
  ```
  别把演示用的"喝水""写周报"留在用户的 App 里。如果调过视窗尺寸，也恢复回去。
  **清之前、往里塞示例数据之前，先看一眼里面是什么，不只是有哪些键。** 预览面板用户也看得到、也会点着试：
  有一次里面是一条随手敲的"q'sqwl"——用户自己建的，却被当成测试残留清掉了。
  看起来像用户留下的，就先问一句。

### 7. 如实汇报

说清楚：做了什么、测试多少条全绿、变异测试试了哪几个、有没有没做完的、有没有你不确定的地方。
测试没过就说没过，跳过的检查就说跳过了。用户信这套流程，是因为汇报可信。

**git 由用户自己提交。** 他明确说过"你教我怎么 commit 就行"。给他现成的命令，别替他跑。

## 和用户怎么说话

- 用户是零基础但学得很快，而且**想懂原理**。解释新概念时给一句类比，别堆术语，
  也别过度简化到失真。他问过"我该学哪些设计知识"，说明他要的是能带走的知识，不只是结果。
- 他的反馈往往是体感："不太丝滑""经常误触""主次不分明"。
  **别照字面改，先翻译成具体的交互问题**。"必须按前面的地方"翻译过来是
  "拖拽手柄太小，应该整行都能拖 + 长按浮起"，照这个改才对。
- 拿别的 App 截图来时，先问清是**参考功能**还是**参考视觉**——这两件事的做法完全不同。
- 需要他做决定时用选择题，两三个选项，标出推荐哪个。

## 说好以后要做、需要我主动提醒的事

用户说过"你先记着，等你觉得该做的时候提醒我，我怕我忘了"。这两件由我负责开口：

- **组件样板页 `tools/gallery.html`**——一页展示所有组件的所有状态。
  **提醒时机**：下次要改 `:root` 里的设计变量、调整视觉风格，或用户拿别的 App 截图来对比视觉时。
- **待办列表的大数据量测试**（500 条任务的渲染耗时）。打卡那边已经做了 3650 条记录的版本。
  **提醒时机**：用户第一次说"有点卡"，或任务数量明显变多时。

明确**不做**：截图对比式的视觉回归测试。要引入一堆依赖和基础设施，
会破坏"零依赖、每行都看得懂"这个前提——而那正是这套工具好用的原因。

## 详细资料

写代码前看第一个，写测试前看第二个，**动手之前扫一眼第三个**：

| 文件 | 什么时候读 |
|---|---|
| `references/architecture.md` | 要加功能、改结构、写新组件时。代码怎么组织、依赖注入怎么用、状态怎么重置、样式变量怎么用 |
| `references/testing.md` | 要写测试或做变异测试时。测试怎么写、怎么挑变异点、三种坏测试长什么样 |
| `references/pitfalls.md` | 每次动手前扫一眼。缓存、时区、手机端、标识符——这些坑都真实付出过代价 |

项目现状和已有测试清单在 `README.md` 和 `tools/README.md` 里，那两个记录的是"已经做了什么"，
这里记录的是"该怎么做"。
